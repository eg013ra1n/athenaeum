Plate Solving Architecture: Where Does Each Piece Live?

Three crates need new code: rustafits (pure algorithms), athenaeum-core (I/O + orchestration), athenaeum-tauri/web (commands/routes)

A

Composable Modules (Requirements Doc Approach)

Each algorithm is its own module with a focused API. CatalogEngine + PlateSolveService orchestrate them.

rustafits/src/
analysis/ (existing star detection)
platesolving/
pattern_matcher.rs — quad hash build + match (trait: QuadHasher)
quad_distance.rs — astrometry.net approach A
quad_interior.rs — tetra3 approach B
ransac.rs — outlier rejection
transform.rs — affine/projective/SIP fitting
wcs.rs — WcsSolution (pixel↔sky, FITS headers)
projection.rs — gnomonic TAN projection
proper_motion.rs — epoch propagation
types.rs — CatalogStar, StarMatch, SolveHints, etc.
athenaeum-core/src/
catalog/ — HEALpix binary format, cone search, memmap
plate_solve/ — PlateSolveService orchestration + DB storage
athenaeum-tauri + web
commands/plate_solve.rs — thin wrappers with progress events
routes/plate_solve.rs — HTTP + SSE equivalents

Pros

  • Each module testable independently
  • Registration reuses PatternMatcher without CatalogEngine
  • Matches the well-designed requirements doc
  • QuadHasher trait lets us benchmark both approaches

Cons

  • More files and interfaces to maintain
  • More complex dependency graph between modules
B

Monolithic Pipeline

Single plate_solve() function in athenaeum-core that calls rustafits internally. Less composable but fewer moving parts.

rustafits/src/
platesolving.rs — everything in one 1500-line file
athenaeum-core/src/
plate_solve.rs — catalog + orchestration + storage in one module

Pros

  • Fewer files to navigate
  • Simpler to implement initially

Cons

  • Hard to reuse for registration (different pipeline)
  • Hard to test individual components
  • Single file grows unwieldy fast
  • Can't swap quad hash implementations cleanly
C

Hybrid: Modules in rustafits, Simple Service in core

Keep rustafits modular (same as A) but simplify athenaeum-core to a single service module instead of catalog/ + plate_solve/ separation.

rustafits/src/
platesolving/ — same modular structure as A
athenaeum-core/src/
plate_solve/ — CatalogEngine + PlateSolveService + DB ops in one module dir
mod.rs, catalog.rs, service.rs, storage.rs

Pros

  • rustafits stays clean and composable
  • athenaeum-core simpler — one domain module
  • Still testable at the algorithm level

Cons

  • catalog.rs may grow large with download + conversion + cone search
