# Catalog: database, settings, coordinates, FITS

> Moved verbatim out of `CLAUDE.md` on 2026-09-22. This file is the reference for the subsystem; `CLAUDE.md` keeps only the rules, the file map and a pointer here. A cycle that changes this subsystem updates THIS file (acceptance paragraphs, rulings, measurements) and touches `CLAUDE.md` only if a rule or a path in its summary changed.

## Database

Schema in `crates/athenaeum-core/src/db/schema.rs::init_db()` (idempotent `CREATE TABLE IF NOT EXISTS`). For dev-reset path see auto-memory `MEMORY.md` → "Database issues".

Key tables:

- `files` — physical files (path, filename, size, format, modified_at).
- `frames` — FITS/XISF metadata + RA/Dec/coordinates/temps/optics. `frames.override` = "user has edited; scanner must not undo".
- `fits_header` — raw header blob, used by metadata-pane revert.
- `scan_roots` — monitored directories.
- `frames_set` + `imaging_nights` + `sessions` + `session_members` — frame-set/session lifecycle. **Frame sets are global, not project-scoped** (the `projects` table is vestigial; `project_id` parameters are accepted but ignored). **A night is the grouping unit, not the calendar date**: the Analysis / Coverage tree groups by `imaging_nights.id` and labels the span (`October 18–19, 2025`), and the Shoot Calendar keys each day on the night that STARTED there (`DATE(imaging_nights.start_time, '-12 hours')` for organized frames, the same noon-to-noon rule over `date_obs` for loose ones) — `get_calibration_hierarchy_for_frame_set` used to group by `DATE(f.date_obs)`, which cut every through-midnight night in two (the original LDN 1272 report). **Nights are derived data, never stitched**: every merge (manual `api::frame_sets::merge_frame_sets`, `auto_merge`) and the `recalculate_frame_set_nights` command re-derive a set's nights/sessions from the union of its member frames via `sessions::rederive_for_frame_set` (delete the set's night rows — sessions/members cascade — then `detect_sessions` over the whole membership; a member without DATE-OBS lands on a fallback night, never dropped). Matching night rows by calendar date + range overlap is what stored one night as two rows after a post-flip merge (LDN 1272, 2026-09-05) — `frames_set_merge.rs` is gone with it.
- `calibration_set` + `calibration_set_frames` + `calibration_set_to_frames` — grouped calibration frames + consumer links.
- `tags` + `frame_tags`, `settings` (the `export_templates` table, created in `db/schema.rs`, and `sync_sources`, created by `sync/store.rs`'s `DDL_SYNC_SOURCES`, are vestigial — no feature reads them).
- `master_lights` — what a stacking run WROTE (M4d, ruling R-M4d-4): one row per written output (`kind` = `master | drizzle | weight_map`), `UNIQUE(run_id, group_key, kind)`, cascading with its `stacking_runs` row. **A master light is cataloged here and NOWHERE else** — it never becomes a `frames` row (the scanner's `CALSTAT` + `ATH_CSRC` skip rule is untouched).
- Archive: `archive_roots`, `archive_operations`, `archive_operation_files`, `archive_operation_steps`; `frames_set.archived_at` + `archive_operation_id`; `files.archived_in_operation` + `archive_zip_path` + `archive_path_in_zip` + `archive_entry_crc32`.
- Zips: `zip_archives` (one row per zip read or built; `size = 0, modified_at = ''` is the retry sentinel), `zip_released_entries`, `black_hole_zips` (a sibling of `black_hole`, keyed on `zip_id`, never on `original_path`). See **Zips in the catalog** below.
- File-op: `file_operations`, `file_operation_files`, `file_operation_steps`.

Indexes on `filename`, `date_obs`, `object`, `instrume`, `ra`, `dec`, `objctra`, `objctdec`, `exptime`, `filter`.

**Scanner re-parse is non-destructive.** When a scanned file's `(size, modified_at)` drifts, the scanner re-parses and UPDATEs the existing `files`/`frames`/`fits_header` rows in one transaction so `files.id` and `frames.id` are preserved — junction tables stay intact across edits, archive→restore round-trips, and FS clock drift. Implemented in `scanner::reparse_and_update_in_place`.

## Settings, Coordinates, FITS

- **Settings precedence**: runtime override > DB > default. `SettingsManager` in `crates/athenaeum-core/src/settings/`. Frontend uses `get_setting` / `set_setting`; Rust commands use `state.settings`.
- **Frame-set clustering threshold**: `grouping.threshold.value` (default `3.0`) + `grouping.threshold.unit` (default `deg`; also `arcmin`, `arcsec`). Read internally via `SettingsManager::get_grouping_threshold_arcsec`.
- **Coordinate parsing**: `parse_ra_to_degrees` / `parse_dec_to_degrees` in `crates/athenaeum-core/src/coordinates/` accept decimal, HMS/DMS, and colon-separated formats.
- **FITS parsing is hand-rolled** (`fits_parser/fits_header_reader.rs`) — no fitsio/CFITSIO dep; reads 2880-byte blocks until `END`. Image *rendering* (pixels) is the `rustafits` submodule via `rustafits_processor/`.
- **XISF parsing**: XML header per XISF 1.0 spec.
- **Frame-set clustering** (`clustering/`) is seed-and-grow single-link on RA/Dec for LIGHT frames, great-circle distance, recomputed center on each member add. Frames already in any set are excluded by `auto_generate_frame_sets`.
- **Duplicate detection**: three keys, all XXH3_64, deliberately not interchangeable (spec `docs/superpowers/specs/2026-08-27-duplicate-detection-design.md` §2.5). Default: raw sub-frames by `fits_header.header_fingerprint` (+ size + filename, zero I/O), masters/processed by `files.strong_hash` (full file, header-shortlisted). Opt-in `duplicates.use_content_hash`: everything by `files.content_hash` (3 × 512 KB sampling). `content_hash` has ONE bulk producer — the content-index job (`api::content_index`, autostarts after a scan when sync is configured or content grouping is on; never the scan itself); `strong_hash` is banked by every full read (master-hash pass, deep verify, sync manifest/confirm/ingest) via `db::bank_strong_hash` under the `disk_matches_row` staleness contract. One full-hash function: `package::xxh3_full_file`. **The master-hash pass is the expensive half of scan Phase 4** (measured 2026-09-17: the two cache rebuilds + the O(folders²) folder pass total ~3.6 s on a 40k-file catalog, while the pass reads every shortlisted master in full at the volume's speed — 11.7 MB/s on the owner's SMB share), so it reports as its own scan phase `"hashing"` (per file, with the path; UI label "Verifying master duplicates") and `"caching"` names only the rebuild. Phase 4 never runs on a scan that found nothing new or modified (`new_files.is_empty()` returns first). The content index yields to any active scan (`run_content_index_yielding` parks in 500 ms steps while `ServiceContext::active_scans` is non-empty) — its per-chunk nap does not protect a scan walking the same volume. `docs/superpowers/research/2026-09-17-duplicate-cache-scan-measurement.md` has the numbers.
- **Export**: WBPP folder/keyword export only (`WbppExportConfig` in `crates/athenaeum-core/src/export/models.rs`; modules `data_collector`, `file_organizer`). Symlinks on unix; the Windows symlink branch exists but is unreachable from the UI. There is NO token-templating engine (`{OBJECT}`-style tokens and the `export_templates` table are doc/schema leftovers — see `docs/export/README.md`). **The `rawWithCalibrationSets` mode lands raw originals, never Athenaeum-built masters**: a master build repoints every consumer link onto the master, so the collected tree names the master; `data_collector::resolve_raw_calibration_sets` swaps each built master back for the raw set it superseded (following the raw set's own links), keeps imported masters with a warning, and stats every substituted original — originals not on disk block the mode up front via `ExportReadiness.missing_raw_calibration_files` (same pattern as `missing_master_files` for the calibrated mode).



## Zips in the catalog (zip plan, 2026-10-28)

Spec `docs/superpowers/specs/2026-10-27-zip-archives-in-catalog-design.md`; probe numbers `docs/superpowers/research/2026-10-27-zip-probe-measurement.md`. Archive-side rules (our Move and ZIP rows, rollback, partial Unarchive): `docs/archive/README.md` -> Zip archives in the catalog. Code: `crates/athenaeum-core/src/zip_store/` (`mod.rs` says: no other module opens a zip).

**Rules that bite**

- **A zip is read-only and metadata-only at scan time.** The scanner reads a zip's central directory and, per frame entry, the header bytes through a 4 KiB `BufReader` (measured 0.06% of a zip at 4 KiB, 9% at 1 MiB; extraction uses 1 MiB). Never read a whole zip or a whole entry in a scan. An unchanged zip (same `size` + `modified_at` as its `zip_archives` row) costs one `stat` and logs nothing; a rescan that logs `bytes_read` for an unchanged zip is a bug.
- **Nothing reads `files.path` of a zip-resident row.** Pixels and whole-file bytes come from `zip_store::materialize` / `materialize_paths` (catalog path strings in, local paths out; a disk row or a path not in the catalog passes through). Hold ONE `Materialized` per batch operation where the frames are known up front; `materialize_one` is for a genuinely single action, because each pin drop scans the cache dirs for eviction.
- **Missing never deletes.** A zip-resident row is present when its zip exists and the entry is in its directory; a missing or unreadable zip makes its rows missing (`zip_store::presence::{row_is_present, present_flags, catalog_path_is_present}`; both hosts' missing-files checks call `present_flags`, which reads each zip's directory once, so the hosts cannot drift), never deleted. Entries that vanish from a changed zip become missing too. Relink reports `zipsMissing`; a root whose zips are gone for good can only be removed.
- **The three hashes keep their jobs.** Scanning gives a zip-resident row no `content_hash` and no master full-hash pass (both would read whole entries over the network), and the content-index job skips such rows. `strong_hash` (full-file xxh3) and `content_hash` (the 3 x 512 KiB sample) are banked when an entry is first fully extracted and verified. Until then a zip/disk pair groups only under the default header-fingerprint key, not in content-hash mode. A row of OUR Move and ZIP is verified on extraction against the plan's `expected_hash`, which is the SAMPLED hash: never compare it with `strong_hash` (`docs/archive/README.md`).
- **Black Hole is keyed on `zip_id`.** `black_hole_zips.original_path` does not follow a rename and is display history only.

**Rows.** A foreign zip-resident row: `files.path` is the virtual path `<zip path><SEP><entry path with SEP>` (so `files.path` stays UNIQUE, survives the separator-strict prefix swap of a folder rename, and reads naturally in logs), `files.size` is the entry's uncompressed size, `modified_at` its ZIP timestamp, `format` the entry's FITS/XISF. Both foreign and our rows carry `archive_zip_path`, `archive_path_in_zip`, `archive_entry_crc32`; core's `file_location` gives `Disk` or `Zip`. A zip with no frame entries still gets a `zip_archives` row (`frame_entries = 0`) so the next scan skips it by stat, but is not shown in the browser.

**What a scan does with a zip.** Both walkers take `.zip` beside the frame extensions and prune `.athenaeum`, `.athenaeum_staging` and `.athenaeum_restore_temp` (an archive root may sit inside a scan root, so our temp copies are never cataloged). Frame entries are `fits`, `fit`, `fts`, `xisf` (case-insensitive); skipped with a log line: `__MACOSX/` and `._*` AppleDouble entries, encrypted entries, entries that are themselves `.zip` (and split zips), absolute names or names with a `..` component. The calibrated-light skip (`CALSTAT` + `ATH_CSRC`) applies to entries too. An entry already owned by a row (our Move and ZIP rows) or released while a disk row with the release's fingerprint has its file (see Releases below) is skipped. For a new entry the header is parsed with the same code as a disk file (so `header_fingerprint` is computed exactly the same) and then either:

- **adopts a row that moved into the zip**: the same fingerprint match, "old path is gone" test and offline-root guard as the scanner's moved-file rule; the row becomes zip-resident and keeps its analysis, plate solve, frame-set membership and calibration links (an already cataloged night zipped outside the app keeps its frame count). A zip-resident row whose own zip is gone may also be adopted by an entry elsewhere (a zip moved or renamed outside the app; the gone zip's `zip_archives` row, creator and released entries follow, and so do the `archive_operation_files.target_zip_path` of the entries the new zip holds, so Unarchive still finds it; entries the zip's own operation copied in stay rowless there too); or
- **inserts a new row** with the virtual path. If the old file still exists the entry is a new row and a duplicate: the Duplicates page shows the pair, exactly as two disk copies.

The reverse is closed: a disk file never adopts a zip-resident row (otherwise a manually unzipped copy would take over an archived row while its zip markers stayed set); it is a new row and a duplicate. A zip with a failed entry is stored with the retry sentinel and read again next scan. Keywordless XISF files embed their path in the fallback header text, so a disk copy and a zip copy never pair on it (pre-existing, accepted).

**The extraction cache.**

| Item | Rule |
| ---- | ---- |
| Location | Desktop: the OS cache directory (`ZipCache::bind_dir`); web/Docker: `<app data dir>/zip-cache` (the DB's parent). `$ATHENAEUM_ZIP_CACHE` overrides both and is single-instance: two processes sharing it ignore each other's pins. |
| Layout | `<cache>/<key>/<entry file name>`; the key is a hash of zip path, entry, zip size + mtime and CRC32, so two zips holding the same entry path never collide and a changed zip never serves stale bytes. Exports and logs see the real file name. |
| Limit | Setting `archive.zip_cache_limit_gb` (Settings -> General -> Archive, default 32, whole number; garbage falls back to 32 with a warn). It is a target, not a ceiling: pins keep an operation's files, an operation larger than the limit still runs, and the cache shrinks back (least recently used unpinned first) when the pins drop. Prepare keeps a group's pins until its fan-out ends, so the cache can exceed the limit by one group. Callers set the limit from the setting before `status()` / clear (`ZipCache::set_limit_bytes`). |
| Status / clear | `get_zip_cache_status` (bytes, entries, limit), `clear_zip_cache` (removes unpinned entries; "Clear cache" beside the limit). |
| Safety | Two callers asking for the same entry share one extraction; extraction streams to `<name>.partial`, checks CRC32 and size, then renames, so cancellation and a vanished share leave no partial; a copy that failed its check and could not be removed is poisoned and never served. Opening the cache sweeps `*.partial` files of processes that are no longer running. |

**Presence and the consumers.** The missing-files check (desktop and web route) no longer excludes archived rows blindly: a zip-resident row is checked through its zip. Consumers decide "is it there" with `catalog_path_is_present` (calibration export, master rebuild, stacking readiness) so a "restore from archive first" blocker fires only when the bytes are reachable nowhere. A failed entry fails that frame with "<file> is inside <zip>, which is not reachable"; the caller keeps its existing per-frame failure policy. Batch dialogs show "From zip: N files, X GB" from `estimate_zip_extraction`; single-frame actions extract without asking.

**Permanent unpack (`unpack_zip_frames`).** For a frame set (its lights plus the calibration frames it reaches) or a calibration set, extracts each FOREIGN entry under a chosen folder (default beside the zip, named after it; the entry's path inside the zip is kept), verifies CRC32 + size, then in one transaction points the SAME row at the new file (same `files.id`, frame, analysis and plate-solve rows) and records `(zip, entry)` in `zip_released_entries` so a rescan does not re-add it. A target that already holds the identical bytes is adopted; anything else there is a conflict and the row stays zip-resident (never overwritten). The zip is always kept. Rows of our Move and ZIP are restored with Unarchive instead. Instrume of an unpacked frame keeps the zip scan root's value. There is no cancel yet (both hosts pass a fresh flag; the dialog says so).

**Releases: the link is a row id (2026-10-29).** `zip_released_entries` holds `(zip_id, entry_path, file_id)`; `file_id` is the row the unpack (Unpack, Unarchive with the zip kept, a hand-unzipped archived frame) moved to disk, `ON DELETE SET NULL` so Void clears it. The link is alive iff that row has `archive_zip_path IS NULL` and its file exists on disk, or sits under an offline scan root. The ONE rule is `zip_store::scan::classify_releases`, run on every scan of a zip, changed or not: alive = the entry stays out of the catalog; not alive = the release is deleted and the entry takes the normal path, the linked row first (same id, plate solve, set memberships; only if it is still a disk row of that frame, same fingerprint), then `find_moved_row`, else a new row. A different row with the same fingerprint (an original elsewhere) never keeps a release alive. `header_fingerprint` is only the fallback of a release with `file_id` NULL from before the link (migration links it when exactly one disk row carries the fingerprint). `list_zip_entries` is read-only: `released` + `copyPath` only while the link is alive.
A scan over several roots (the monitor cycle, the desktop "find new frames" scan; `scanner::run_registered_scans`) walks the frame files of ALL its roots before it reads any zip, so a copy unpacked from a zip in root A and moved into root B is found in B by its row's move rule instead of being taken back into the zip by A's pass. A scan of ONE root keeps the old order (its files, then its zips), so moving a copy to another root and then scanning only the zip's root still takes the row back into the zip and makes the moved file a new row: scan the roots together (the monitor does).
A release recorded for an entry with no catalog row is not recorded at all (Unarchive with the zip kept, a Copy entry): it has no link, would be dead on the next scan, and would make an unchanged zip read and warn "changed zip". A NEW zip's entry never takes a row that is linked to a release of another zip that still exists; that zip's own scan takes it back (a vanished zip's release does not hold its row back).
Reading an entry the catalog has no row for (link gone, skipped, not yet scanned; frame names that are safe only): `get_zip_entry_header` parses its first bytes live and `preview_zip_entry` renders it from a zip-cache extraction keyed like a row of that entry; neither writes to the catalog, the zip view shows it as a frame row (metadata on pick, preview on double-click) and a scan catalogs it later.

**Removing a folder forgets its zips.** `db::delete_scan_root` deletes every `zip_archives` row under the root (separator-strict prefix on `zip_archives.path`, in the same transaction as the root's `files` rows; `zip_released_entries` and `black_hole_zips` go by cascade), so a re-added folder catalogs its zips from scratch. Files on disk are never touched. `archive_operations` stay as history; Unarchive of a surviving operation reads its zip from disk as before.

**Whole-zip operations.** A zip rename/move rewrites `zip_archives.path`, `archive_zip_path`, the virtual `files.path` of its foreign rows and `archive_operation_files.target_zip_path` with the separator-strict prefix swap, also when a folder holding zips is renamed or moved (`zip_store::catalog`; `docs/file-browser/README.md`). Relink applies a root swap to zips too (`zips_moved / present / missing`).

**Accepted in v1.** Project stacking of zipped LANDED files is effectively unreachable (`landed_unchanged` treats virtual paths as gone). Our Move and ZIP rows keep their original `files.path` on the old root after a relink (a folder rename moves it). Unpacked frames keep `frames.instrume` from the zip's scan root. Candidate follow-ups: `ZipShapes::load` is eager (an attested OSC plus debayer used to cost no zip reads); `zip_resident_master_block` says "not reachable" also when the zip is reachable but lacks the entry.

## Calibration geometry (2026-10-20)

**A calibration set of another frame size never calibrates a frame** (owner ruling 2026-10-20). Size is `frames.naxis1 × frames.naxis2` — the stored array, so after binning (binning stays its own matcher parameter); a set's size is its members' agreed size, and a set whose members disagree ("mixed sizes") fits nothing. It is not a `MatchMode`: no setting relaxes it, and no manual choice either. The app never crops: calibration happens only when sizes match. A side that records no size blocks nothing (a `debug!` per candidate-engine call, one `warn!` per Find Calibration call or readiness pass). The rule lives in `calibration::geometry` (`fit`, `geometry_for_frame`, `geometry_for_set`, `geometry_for_frames`, `LazyFrameGeometry`).

**The sub-frame origin** `XORGSUBF`/`YORGSUBF` (where a same-size crop sits on the sensor) is read from the stored header blob — a set's: its lowest-frame-id member's — and compared only when both sides record it. Owner ruling G-7 ("auto no, manual yes"): auto-link never links a set at another recorded origin, and Find Calibration removes such an automatic link; a person may choose it by hand — the picker shows it selectable with a warning badge, the assignment is accepted with a `warn!`, and the hierarchy, the export readiness (`ExportReadiness.geometry_warnings`) and the stacking plan warn about it, never block. In-app masters stamp the origin their members agree on (G-5, `calibration_library::headers`); a master built before 2026-10-20, or from members that disagree or record none, records none and is not compared on origin until rebuilt.

Where the size rule holds: the candidate engine (`configurable_matcher::find_calibration_candidates` — auto-link and the manual list; verdict `geometry` on every candidate, `mismatch` for size, `warning` for origin); raw-frame grouping (`detect_flat_groups` / `detect_dark_groups` / `detect_bias_groups` take the source's size); the flat pattern path and the on-demand dark/bias path (each group is judged before any set row is written, so a refused group leaves nothing behind); manual assignment (`manual_assign_calibration` / `manual_assign_subcalibration` refuse before writing); the flat pre-calibration chain (`api::masters::select_flat_precal` refuses a linked master of another size); the readiness gate (`ExportReadiness.geometry_mismatches` — a calibrated-lights blocker, the stacking plan's `links` blocker, the collab verdict's `linkCalibration`). Find Calibration removes an AUTOMATIC link that no longer fits (`prune_unfit_auto_links`, warn-logged); a manual link is the user's and stays until the picker clears it — the gates name it. Set formation does not key on size: a mixed set is refused, never split. Plan: `docs/superpowers/plans/2026-10-20-calibration-geometry-plan.md` (rulings R1–R13, G-1–G-8).

**Cost of the header read** (review t3fix-t4-t5 M-5). The size is a column and costs nothing; the origin is one stored-header parse per set. The manual candidate list and the Equipment page (`query_camera_calibration_sets` / `load_set_with_score`) parse one header per set — O(sets), acceptable at catalog scale. The hierarchy view, the readiness pass and the matcher read a set's origin lazily (only when sizes agree) and a light's through a shared cache, so a light's header is parsed at most once per view / pass; the collab gate re-runs the pass per light with a fresh set cache (bounded, about 7 parses per light).

**Acceptance (2026-10-25, owner: accepted).** On a copy of the owner's catalog (frame set 182, Horsehead C11, 164 ASI6200MM lights at 9576×6388), through the release web host: the manual candidate list refuses all 20 ROI darks (6384×4258, 4784×3194 — 1843/1844 among them) on size and offers only full-frame sets; Find Calibration links 164/164 with no link of another size; the plan's `geometryMismatches` / `geometryWarnings` are empty; Calibrate runs all 164 lights with no geometry error. The production catalog no longer held the bug's state (the owner had re-linked set 182 by hand to full-frame darks), so the up-front refusal of an existing misfit link is covered by tests only. The same runs showed set 182's darks are offset-50 masters on OFFSET-1 lights (the 2026-10-02 diagnosis): with them the R/G/B masters are 99.9 % zero; without darks, and with flats rebuilt without pre-calibration, the set stacks cleanly.

### Catalog (database, settings, coordinates, FITS)

Schema in `crates/athenaeum-core/src/db/schema.rs::init_db()` (idempotent `CREATE TABLE IF NOT EXISTS`, serialized by `INIT_DB_LOCK`). Desktop DB in the OS app-data dir; `/data` or `$ATHENAEUM_DB_PATH` in Docker. Dev-reset path: auto-memory `MEMORY.md` → "Database issues". Reference: `docs/catalog/README.md`.

- **Key tables**: `files` (physical files) · `frames` (metadata; `frames.override = 1` = user-edited, the scanner must not undo it) · `fits_header` (raw blob, the revert source) · `scan_roots` · `frames_set` + `imaging_nights` + `sessions` + `session_members` · `calibration_set` (+ `_frames`, `_to_frames`) · `tags`/`frame_tags` · `settings` · `master_lights` (what a stacking run WROTE — a master light is never a `frames` row) · the archive and file-op tables. `projects`, `export_templates`, `sync_sources` are vestigial.

- **Scanner re-parse is non-destructive**: a drifted `(size, modified_at)` UPDATEs `files`/`frames`/`fits_header` in place (`scanner::reparse_and_update_in_place`), so ids and junction rows survive edits and archive round-trips.

- **FITS parsing is hand-rolled** (`fits_parser/fits_header_reader.rs`, no CFITSIO); pixel rendering is the `rustafits` submodule via `rustafits_processor/`; XISF per the 1.0 spec. Coordinates: `parse_ra_to_degrees`/`parse_dec_to_degrees` accept decimal, HMS/DMS and colon forms. Frame-set clustering is seed-and-grow single-link on LIGHT frames' RA/Dec.
- **Duplicate detection**: three XXH3_64 keys, deliberately not interchangeable — `fits_header.header_fingerprint` (raw subs, zero I/O), `files.strong_hash` (masters, full file, banked by every full read), `files.content_hash` (opt-in sampled; its ONE producer is the content-index job, never the scan). The master-hash pass is the expensive half of scan Phase 4 and reports as phase `"hashing"`; the content index yields to an active scan.
- **Export** is WBPP folder/keyword export only, no token-templating engine (`docs/export/README.md`); the `rawWithCalibrationSets` mode lands raw originals, swapping every built master back for the raw set it superseded.
