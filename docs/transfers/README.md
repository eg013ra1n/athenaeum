# Transfers / personal sync (batch model v2.1)

> Moved verbatim out of `CLAUDE.md` on 2026-09-22. This file is the reference for the subsystem; `CLAUDE.md` keeps only the rules, the file map and a pointer here. A cycle that changes this subsystem updates THIS file (acceptance paragraphs, rulings, measurements) and touches `CLAUDE.md` only if a rule or a path in its summary changed.


Device-to-device transfers over iroh (specs: `docs/superpowers/specs/2026-07-20-transfers-status-v2-design.md` + `2026-07-21-transfers-batch-model-design.md`). Core in `crates/athenaeum-core/src/sync/` (engine/receiver/store/status/ingest) + `sharing/` (wire).

- **Row = TRANSFER, attempt = counter.** `sync_outbound`: one row per transfer; Resend RESETS the same row (`generation`+1, fresh per-attempt `wire_package_id`, files→pending) — never mints rows. `sync_inbound`: one row per `(peer, batch_uuid)`; a new attempt's announce upserts it. `generation` is the user-facing "attempt N" (the `attempts` column also counts announce-retries — never display it). Receiver-cancelled transfers are FINAL: a resend gets an all-cancelled ack (receipt re-key), no fetch.
- **Receiver-declined transfers — Resend mints a NEW transfer** (Task D, `api::sync::resend_declined_as_new_transfer`, keyed on `last_error == CANCELLED_BY_RECEIVER_DETAIL`): the app renames the payload dir to a fresh uuid basename (⇒ new wire `batch_uuid`), clones the manifest, and enqueues a new row (worker inserts it — no API pre-insert); the old declined row is kept as history with its Resend affordance recomputed dead. Decline stays final per the OLD `batch_uuid` (receiver gets a brand-new inbound row for the new one; its old declined row is untouched). Perseus resend is UNCHANGED — it re-uses the same dir/basename and still bounces all-cancelled (autonomous agents must not override a human decline). `retry_sync_package` may now return a NEW id (frontend `useTransferQueue.ts::resend` branches on `newId !== id`).
- **Wire**: `Msg::Announce3` = name + full file manifest + `batch_uuid` (sent basename == `outbound_package_key`); `Msg::Revoke{package_id, reason}` fires on ANY sender terminal with an outstanding un-acked announce (cancel/superseded/failed) — Revoke IS the stop mechanism (iroh-blobs providers can't unilaterally abort; the receiver's ingress pump signals `InboundControl::request_revoke_abort` so an in-flight fetch aborts promptly, then that peer's lane does the bookkeeping). v1/v2 announces still decode (`batch_uuid := wire id` fallback). `Msg` postcard indices FROZEN: append-only, golden pins in `sharing/wire_golden_tests.rs`.
- **Upgrade = clean reset**: first init without `sync_inbound.batch_uuid` (checked BEFORE any DDL — catches beta.1/2 shapes with no sync_inbound at all) wipes all 8 transfer tables in one tx; catalog untouched. `init_db` is serialized by `INIT_DB_LOCK` (concurrent double-init raced the DROP+CREATE trigger reinstall once).
- **Structured rel_path**: object sends use the WBPP hierarchy (`export/file_organizer.rs::compute_wbpp_placements`, shared with export); browser sends preserve source-relative paths. Receiver lands at `<incoming>/<sender_slug>/<batch_slug>/<rel_path>`, `landing_dir` persisted → attempts land in the same tree.
- **Per-file state persisted both sides** (`sync_*_files`, reset per attempt): bytes checkpointed on transitions only (live bars ride `sync-file-progress`, `file` = FULL rel_path). Dedup handshake (Offer/Want vs catalog) runs before every attempt — only missing files travel; all-duplicate → confirm without transfer (`already on peer`).
- **State ⊥ error**: `displayState` shows benign `waiting`+`stalledUntil` when a retry is armed; `last_error` auto-clears on the first serve tick; `failed` = local-fatal only (delivery-forever). `Delivered` = "uploaded — awaiting confirmation", non-terminal. Received history + delete key on `batch_uuid` (B5b); `InboundSummary.lastError` carries revoke reasons.
- **Lifecycle plumbing at startup** (spawned post-`ensure_started`): `resurrect_pending_senders` (account-device peers only — collab-only rows skipped) + orphan sweep (row-less payload dirs age-gated by recursive max-mtime ≥5min; orphan `in-flight/` tags). Tag namespaces are CONTRACT: transfer machinery owns `in-flight/…`+role pkg tags, collab seeding owns `project/…` (live since D3) — sweeps never cross.
- **`sync_events` journal** (capped 200/batch) — connection noise lives here (`list_transfer_events`), NEVER in the status string. Storage: `get_transfer_storage`/`cleanup_finished_transfers` (Settings → Sync; blob bytes return within the ~15min GC window — no on-demand GC in iroh-blobs 0.103).
- Frontend: master-detail `src/pages/Transfers.tsx` — one row per transfer comes FROM THE MODEL (no collapse/supersession compensation); delete keys on `batchUuid` both directions; device names via `get_sync_device_names`, node-id hex only in Details.
- **Parallel receiving (W2)**: the receiver runs PER-PEER lanes (`receiver.rs` — router keyed on `event_peer(&ev)`, exhaustive match, no wildcard) — different devices' transfers overlap, one device's events stay strictly FIFO (every serialization-protected key is peer-owned: `(peer,batch_uuid)` rows, revoke flags, `staging/<wire_id>`, sender-slug landing trees; device-NAME collisions are still safe via conn-mutex atomicity in `resolve_landing_dir`). Concurrency capped by `ReceiveGate` on `InboundControl` (`sync.max_concurrent_receives`, default 2, clamp 1..=8, live via `set_sync_max_concurrent_receives` both backends) — acquired AFTER the cheap short-circuits (replay-acks/declines never wait). The wait is INTERRUPTIBLE: a parked transfer that is declined or revoked leaves the queue without a permit (`abandon_parked_receive`, re-checked on every wake AND once post-acquire, both before the `Fetching` stamp) — it must never overwrite a row the decline command already closed (resurrecting it to `fetching` made it unclearable: `delete_transfer_history` refuses non-terminal rows), and a revoke's bookkeeping must never queue behind a permit. A parked decline does NOT run `cancel_epilogue`; the sender's next announce hits the declined-final bounce above the gate. Ingest locks the store conn PER FRAME (`IngestConn::Shared` + a `yield_now` after each release — std Mutex is unfair, without the yield a waiter starves the whole package), never across a package. Accepted risk (documented in the router comment): staging keyed by sender-minted wire id alone; peer-scoped staging is a named follow-up.
- **Upload speed limit (W1)**: `sync.max_upload_bytes_per_sec` (0 = unlimited, floor 100 KB/s) caps the DEVICE-wide sync egress via iroh-blobs' `ThrottleMode::Intercept` — the provider awaits our rpc reply per ~16 KiB payload chunk, so DELAYING the reply is the throttle; the reply must NEVER be dropped or `Err` (both abort the peer's download — the consumer's Throttle arm in `sharing/iroh/mod.rs::build_router` is load-bearing). `UploadPacer` (leaky bucket, idle earns no credit) lives on `SharedIrohNode`; applied at bind in `ensure_iroh_node` + live via `set_sync_upload_limit` (both backends) / Perseus `max_upload_mbps` (TOML + `PUT /api/upload-limit`). Uploads only — a download cap is impossible at app level (the byte loop is inside iroh-blobs); the fleet-wide upload caps bound downloads implicitly.
- **Perseus web UI v2** (spec `2026-07-23-perseus-ui-v2-design.md`): two-tab Nord page (`crates/perseus/src/web/{index.html,app.js,style.css}`, include_str!-embedded, no npm) — Transfers tab = grouped `GET /api/transfers` model (one row per batch across fan-out targets) + obligation-gated `POST /api/delete-files` (source cleanup; decline/cancel close obligations, failure blocks) + `POST /api/delete` (history groups); pre-v2 `/api/sent|history|batches` retired. Received transfers carry the sender kind: `sync_inbound.peer_capability` stamped at announce, `InboundSummary.peerKind` + `get_sync_device_capabilities` (both backends), Perseus badge on received rows.
- **Multi-source project distribution (D3)** — *package era, retired for collab by "Collab v3 — per-frame exchange" below (2026-09-24); `fetch_collection_multi` and the assignment loop stay for personal sync* (spec `2026-07-26-multi-source-project-distribution-design.md`): published collab packages download swarm-style from EVERY member holding them — `fetch_collection_multi` (per-child provider fan-out with byte-resume failover; iroh-blobs split telemetry is LOSSY, byte counters are the only oracle), staging in `collab_swarm/<pkg>` (never `staging/` — collides with the push path). Publish imports the package dir as a collection FIRST (its first seed) and POSTs the REAL root hash; legacy identifier-value announcements fall back to the push path with a session-cached `SWARM_UNFIT` verdict. Every successful ingest re-seeds under `project/<pid>/<pkgid>` via `collab_seed/<pkg>` hardlink dirs (`TryReference`; publisher ≈ zero extra disk, a downloader also keeps the store-owned fetch copy — spec §3.4). Auto-replication worker (a 20-min pass, a post-poll pass and a manual per-project sync — all retired since; `collab_projects.auto_replicate` default ON, role-gated) pulls `published ∧ ¬superseded ∧ ¬mine ∧ ¬complete`; UI = per-project toggle + published-bytes + "downloading from N sources" via `project-download-progress`. `fetch_collection_multi`'s per-child fan-out now runs our own assignment loop by default (`sharing/iroh/assign.rs`, `SwarmFetchMode::Assigned` — a progress-deadline stall ceiling plus hedging, in place of iroh-blobs' strictly sequential per-provider walk); `ATHENAEUM_SWARM_FETCH=stock` restores upstream's fan-out for the rest of the process without a rebuild.
- **Perseus 0.5.1 — local library agent** (spec `2026-07-26-perseus-051-local-library-design.md`): the web page grows a **Library** tab — lazy one-directory listing addressed as `(root_index, rel_path)` (absolute paths never travel; ONE containment guard, `library.rs::split_rel`/`resolve_in_root`), status derived with NO new table (batcher pending set × `perseus_batch_files(source_path)` × live outbound × `perseus_seen` → `queued`/`sending`/`delivered`/`declined`/`sent`/`unsent`), plus a rustafits JPEG **preview** (Cargo feature `preview`, in default AND headless; semaphore of 1, LRU-8 whose key IS the ETag) walked with ←/→ as a pre-blink.
- **Deletion is always allowed, always honest** (§2 matrix, `library/delete.rs`): per file pending-remove → audit row → unlink → `seen.mark_deleted`; one file's failure never stops the pass. The audit lands BEFORE the unlink (retention's own contract), so a failed unlink can leave a row for a file still on disk. **Forget seam (T9b)**: the watcher's emitted-paths set short-circuits *before* the seen store, so every in-app deletion (Library *and* retention) broadcasts one batched `WatcherForget::forget` — a re-created file re-enqueues within the run; a file deleted OUTSIDE Perseus gets neither the stamp nor the forget, so its live seen row makes a byte-identical mtime-preserving re-copy count as already sent (restart included) — only a differing size/mtime re-enqueues (deliberate — auto-forget on a stat flap would re-send a night off a blinking share).
- **Scheduler = fire-at-time**, not transfer windows: `[send] mode = "scheduled"` + `schedule_times = ["06:00", …]` + `schedule_catchup`; the batcher's third arm arms `sleep_until(next_fire)`, `last_scheduled_fire` lives in the new `perseus_meta` KV table, and a missed span catches up **once**, never N times for N points. Collisions fall out of drain-at-flush (a manual send in flight ⇒ the scheduled batch carries only post-drain files). UI = 3-way mode radio + HH:MM list editor in the To-Sync strip; `/api/status` carries `nextScheduledSend`.
- **Send anything, anywhere**: `POST /api/library/send` (pulls its files OUT of the pending set first so the next flush can't double-send; replies `{enqueued, skipped, package_ref}`) and Transfers' **Send to device…** (`POST /api/transfers/send-to` — mints a NEW transfer ⇒ new `batch_uuid` ⇒ a brand-new inbound row, rebuilt off `perseus_batch_files` linkage, eligible-subset "97 of 100"). Both dialogs share one `loadSendTargets` read of `GET /api/targets`'s **`runtime`** list = this node's *running engines*, never the account device list; an unresolvable or ambiguous name is a loud `400`.
- **Free space + retention transparency**: `diskspace.rs` = one entry per unique volume (`statvfs` / `GetDiskFreeSpaceExW`), the EXACT requested path only — never resolved to an ancestor, a failed probe drops the chip rather than reporting the wrong disk; `/api/status` `volumes`, chips red under 10 GB (sibling roots on one disk get no chip, by design). Settings' Retention card is generated from the *effective* config, and the per-file fate line anchors on the **earliest** confirmation of the package the file is still live-linked to (`SeenStore::package_for_path`) — `keep_days` never waits for the slowest target, and saying "every target" in the UI would promise a delay the evaluator does not honour.
- **Mirror hierarchy (0.5.2)** (spec `2026-07-27-perseus-mirror-hierarchy-design.md`): Perseus top-level TOML key `mirror_hierarchy` (default TRUE — per-batch is the opt-out; To-Sync checkbox, live via the send-cfg watch — hand-edited TOML included) makes every fresh Perseus enqueue land on the receiver in ONE stable tree `<incoming>/<sender_slug>/<rel_path>` instead of per-batch folders. Layout is STAMPED PER TRANSFER at enqueue (`sync_outbound.layout`, `PackageLayout{Batch,Mirror}` in `sharing/types.rs`): retry keeps the row's stamp, declined-divert CLONES `row.layout` (a decline is not a re-choice of landing shape), send-to-device reads the current setting; desktop senders + collab pass `Batch` (out of v1 scope). Wire: `Msg::Announce4` (= V3 + layout, appended, golden-pinned) is emitted ONLY for Mirror — Batch keeps frozen Announce3 bytes, so unflipped fleets have zero exposure; an OLD receiver can't decode v4 → announce un-acked, sender retries (documented "upgrade the receiver" stance, same as v2→v3). Receiver realization: Mirror ⇒ `landing_override = None` — the pre-v2 (v1) landing path IS the mirror tree; `resolve_landing_dir` untouched, `landing_dir` stays NULL, per-file collisions via ingest's existing `unique_path` (`name_2.fits`, never overwrite). Additive one-way sync: source deletes/renames don't propagate; content-dedup means previously-received files never re-materialize in the mirror tree; mirror-tree root follows the sender's live device name (v1 behavior, renames move it).
- **Frame-set send from the Export tab** (spec `2026-08-28-frame-set-send-design.md`): `enqueue_frame_set_send(frame_set_id, mode, …)` reuses the export pipeline (`collect_export_data → apply_export_mode → check_mode_ready → compute_wbpp_placements`) and feeds `PayloadEntry`s into the one package builder. Four `ExportMode`s (`lightsOnly` / `rawWithCalibrationSets` / `rawWithMasters` / `calibratedLights`); `get_export_readiness` is mode-less and `check_mode_ready` is the single gate for export AND send (`rawWithMasters` is strict — D2). Receiver: a `PayloadKind::CalibratedLight` record lands the file with no `files`/`frames` row and no tracking row at all (calibrated-export v2 §8/§9 superseded D4's reconcile-adopt path — the scanner's blanket CALSTAT+ATH_CSRC skip, see "Calibrated-Lights Export" above, keeps it out of the catalog even if it were ever scanned); after every package `create_calibration_sets_from_scan_with_masters` runs over the ingested (cataloged) frames (D3), so received raw calibration and masters become sets. The app never deletes a sent source (retention is Perseus-only; app-shell retention removed 2026-08-29, `sync_sources` is a vestigial table). Old receivers ingest `CalibratedLight` as frames — "upgrade the receiver". The frame-set send is `render`-gated (`api::frame_set_send` functions + `enqueue_frame_set_send`; `PayloadEntry` stays ungated); the frame-selection send stays ungated for headless consumers.
- **Transfer preparation is a visible, cancellable phase** (spec `2026-08-30-transfer-prepare-and-footprint-design.md` §3): `enqueue_sync_selection` / `enqueue_frame_set_send` keep their signatures but return as soon as the row exists — the per-entry pre-flight is a `stat` (exists, size), never a hash or a copy, and `store::enqueue_preparing` writes `sync_outbound(state='preparing', package_ref=<packages>/<uuid>)` + its `sync_outbound_files` rows in ONE transaction. The work then belongs to `api::sync_prepare::spawn_prepare` (the API layer, not the engine): `PrepareRuntime` on `SyncSenderRuntime` is a `Semaphore(1)` admission slot (two sends must not fight over the source disk) plus a cancel-flag map registered SYNCHRONOUSLY before the task spawns, so a cancel issued the instant the command returns can never miss the flag. Per package the worker reflinks-or-streams each entry into the package dir and hashes it in the same pass (`package::stage_payload`, xxh3 banked as `files.strong_hash` under the `disk_matches_row` contract, a bank failure never fails the send), writes `manifest.ndjson` (`package::write_manifest` — the send path no longer goes through the copying `write_package`, which collab publish and Perseus still use), flips the row `preparing → queued` and sends the engine `Command::Drive(id)`, the same `drive_package` body as `Command::Resend`, told apart only by its log `reason` field. Progress is `sync-progress { stage: "preparing", bytes_done, bytes_total }` throttled ≥ 300 ms; preparation writes **no per-file state** (`pending → sending → uploaded` mean bytes to the PEER), so a preparing row shows the byte fraction against the new `TransferFileCounts.total_bytes`, never `N of M`. `cancel_sync_package` routes to whoever holds the row: raising the preparation's cancel flag is the WHOLE command (the staging loop reads it at every chunk and the WORKER then writes the terminal `cancelled` row, removes the partial dir and settles the per-file rows — stamping a preparing row terminal from an engine would stop no copy), and only a row the flag no longer knows falls through to the engine's `Command::Cancel`; exactly one verdict is ever written (`claim_row` above every outcome + a `Preparing → Queued` CAS), so a cancel that lands in the handover sliver is not overwritten by the promotion. A preparation failure is terminal and NOT resendable (there is no payload), `last_error = "preparation failed: …"`. The engine never resumes a `preparing` row (its dir is half-staged and has no manifest) — `heal_interrupted_preparations` runs at startup above the autostart gate (before any sender is resurrected, and whichever way the gate decides) and turns every one into `failed` ("preparation interrupted by a restart — send again"), removing its dir.
- **One copy per transfer, both ends** (same spec, §4 + §5): the app binds its iroh node with `NodeOptions { serve_import_mode: ImportMode::TryReference }` (`api::sync::ensure_iroh_node`), threaded into `import_package_collection_with_mode` AND `import_subset_collection` (which used to `add_path`, i.e. a silent second copy on every want-subset send) — so `packages/<uuid>` is the only payload copy and the store keeps the collection, the hash-seq and the outboards (64 B per 16 KiB ≈ 0.4 %). Hashes are mode-independent, so the announced `root_hash` is identical either way. The invariant `TryReference` demands — the file never changes after import — is already ours: preparation writes the dir once and no writer ever rewrites a staged payload's content (the declined-divert renames the whole dir, `cleanup_package_payloads` removes it — neither edits a staged file in place). Confirm therefore runs **protect → cleanup → release** on one detached task (`engine.rs::spawn_protect_cleanup_release`): `SharingTransport::protect_shared_before_cleanup` (no-op default; the iroh implementation copies into the store every child another live hash-seq tag also references, so `Owned` wins the union) and cleanup is SKIPPED when it failed — the payload stays on disk rather than being deleted out from under another transfer. A later import probes each referenced child for one byte and re-imports just that file with `Copy` when the read fails (`blobs::ensure_child_readable`): iroh unions external paths and reads the first, so a stale sibling path (the declined-divert rename, a cleaned-up dir) is repaired permanently, not re-pointed. Receiver: `export_child` removes a stale target first (a retry over its own exported file made upstream `reflink_or_copy(p, p)` truncate the inode) and exports with `ExportMode::TryReference`, moving the store's data file into `staging/<wire_id>`; `ingest::land_payload` then hard-links staged → tmp → landing and falls back to a copy on ANY link refusal (cross-device, SMB/NFS/exFAT, permission — `link_or_copy`, a link refusal must never fail a landing), leaving the staged file in place until the package's own epilogue cleanup so the store's reference stays valid. An export whose referenced source vanished (a same-hash sibling cleaned before GC swept the entry) is **transfer-class, never `LocalFault`**: `on_export_source_vanished` drops the receiver's OWN collection tag — a `Waiting` park never calls `release`, and the tag would pin the dead entry against GC forever — the row parks, GC purges within one window (≤ 15 min) and the sender's retry ladder re-fetches. Perseus keeps `Copy` (its resend rebuilds payloads in place, exactly the mutation `TryReference` forbids) and the collab swarm path (`fetch_collection_multi`) keeps its store copies (D3 re-seeds from `collab_seed/<pkg>`). Serve-import progress rides an `ImportProgressSink` the engine hands to `serve` (throttled ≥ 300 ms) — NOT the spec's §4.4 demux route through the transport event channel, which could only have fired after the import it describes had finished — emitting `sync-progress { stage: "indexing" }` from the import's own task while the row is still `queued`.
- **Transfer folders are configurable** (same spec, §6): the old `sync_paths` resolver is now `api::sync::sync_dirs` → `SyncDirs { identity_dir, packages_dir, working_dir, db_path }` and every former `sync_dir.join("packages" | "blobs" | "staging" | "incoming" | "collab_*")` call site reads the matching field. `identity_dir` = `<db dir>/sync` holds `device_key` + `device_key.lock` and **never moves** (the node loads the key from it and opens `blobs/` under the working dir); `packages_dir` = `sync.outgoing_staging_dir` or `<identity_dir>/packages`; `working_dir` = `sync.incoming_working_dir` or `identity_dir`, and owns `blobs/` (one store, every role), `staging/`, the `incoming/` fallback and the collab dirs — both keys in `settings/mod.rs`, empty/unset = the default, which is exactly today's location (an install that never opens the tab changes nothing, and old rows keep their absolute `package_ref`). `validate_transfer_dir` is the single gate for both folders and both backends: absolute + `PathPolicy::check`, no overlap with any scan root (`check_scan_root_overlap` — the scanner would ingest the copies as duplicates), create-if-missing + write probe (a folder it created is removed again when a later step rejects), and the two folders may not be the same nor may the working folder sit inside the outgoing one (outgoing inside working is fine — the default is). Commands `get_transfer_paths` / `set_transfer_paths(outgoing, working)` (`None` = reset to default) / `cleanup_transfer_leftovers` (Tauri + Axum). The outgoing folder applies to the next preparation; the working folder only at the next transport start — `PathSetting.restart_required` (`effective != bound`) drives the "Restart Athenaeum to apply" badge, with no live re-bind in v1. No migration: `get_transfer_storage` reports `packages_dir` / `working_dir` and `leftover_bytes` — `blobs/` + `staging/` of a superseded working dir plus only the **row-less** payload dirs of a superseded packages dir, so a leftover sweep can never delete a package a row still references — and `cleanup_transfer_leftovers` deletes exactly those, refusing while the transport is bound under any of them and clearing the `sync.incoming_working_dir_previous` breadcrumb once they are gone. UI: Settings → **Transfers** tab (`components/settings/TransfersSection.tsx`) — the two folder cards plus the Bandwidth, Receiving and Storage cards moved out of Sync.

## Collab v3 — per-frame exchange (wave 2, 2026-09-24)

Spec `docs/superpowers/specs/2026-09-23-collab-v3-per-frame-model-design.md` (§5, amendments A1–A3), plan `docs/superpowers/plans/2026-09-24-collab-v3-wave2-app-exchange-plan.md` (rulings P1–P26), controller rulings R1–R31 in the plan's SDD ledger. The unit of exchange is ONE calibrated light (a project frame), not a package; the hub (wave 1) keeps the manifest, the app keeps the bytes. Code: `api/collab.rs` (publish, moderation), `api/collab_exchange.rs` (manifest sync, policy, export), `api/collab_autopublish.rs`, `db/collab_frames.rs` (`project_frames_local`), `sharing/iroh/node.rs` (collab store, seed/unseed). **Wave 3 (next section) replaced how frames move:** the version poll, the replication pass, the maintenance loop, the loss guard, the per-frame holder lookups and the full holder reports are gone, and so are their three commands; the bullets below keep only what still holds and say where each retired part went. The wave-2 e2e (`api/collab_v3_e2e_tests.rs`) is replaced by `api/collab_v3_live_e2e_tests.rs`.

- **Folder model (§5.1, P25).** Everything lives under the **Collaboration root** (File Manager → Folders; it IS a scan root, `validate_transfer_dir` with `OverlapRule::Skip`): `<root>/<project slug>/<publisher folder>/<fileName>`. The publisher folder is `sanitize_slug(display name)`, made unique against other publishers in the project and then remembered per `publisher_account_id` (P10) — an account rename never moves files. Own frames go under my own display name. No Collaboration root ⇒ publish and replication refuse with "set a Collaboration folder in File Manager → Folders first"; there is no fallback to the working dir (audit F4). Promoting an existing scan root is allowed only when it already holds `.athenaeum/blobs` or no `files` row lies under it (R5); a failed mount rolls the designation back.
- **The path of a project frame comes ONLY from `project_frames_local.landed_path`** (P26 / A1). Disk truth, holder reports, seeding, the WBPP export and the scanner all read it; none infers a path from the folder layout or a header card. An own frame may live outside the root (seeded by reference). The scanner never creates `files`/`frames` rows under the root: each file there is matched by `landed_path`, then by `(project, xxh3)` (moved or duplicate), else it is an inert foreign file listed in `collab_foreign_files` (R18), whose `size_mtime` spares a re-hash on every scan (R30). The walk skips `.athenaeum/` (P23).
- **The collab store and its ALPN (P1, R4).** A second iroh-blobs store at `<root>/.athenaeum/blobs` (same opener as the personal store, GC on, 900 s), served under `athenaeum/collab-blobs/1` by the unchanged `GatedBlobs`, sharing the device-wide `UploadPacer` (wave 3: GC every 60 s, `COLLAB_GC_INTERVAL`; the pacer is class-aware). The ALPN is mounted ONCE at bind; its handler reads a swappable `Option<mount>` slot (empty ⇒ the connection closes "not mounted"), and `set_collab_root` (own async mutex) opens, sweeps stale `in-flight/project/` tags, swaps the slot and shuts the old store — the router is never rebuilt, so personal-sync connections never notice. Consequence: the ALPN is always advertised. The collab store sits on the root's volume, so a landing is a rename (a Windows cross-volume rename would fail — audit D). Tags: `project/<pid>/<uuid>/<ver>` (raw, one per frame version), `in-flight/project/<pid>/<uuid>/<ver>` while bytes move (P22, R23: kept across a transfer failure for resume, deleted on a permanent failure or when the frame leaves the need set).
- **One copy per machine (the disk ledger).** Publisher: the generator writes the calibrated frame ONCE into `<root>/<project>/<me>/` and the store references it (`add_path_child` without the `Copy` repair — a dead path is reported, never turned into a second owned copy). Receiver: the fetched data file is exported with `TryReference` straight to the final path (`export_child`, P21 — never to a temp, the store would reference a dead path), so the landed file IS the seed. Personal `<working_dir>/blobs` is untouched by collab.

  | ---- | ---- | ---- |
  | Publisher, peak | 3 calibrated copies | 1 + the generator's sibling temp during its atomic rename |
  | Publisher, steady | 2 | **1** (outboard ≈ 0.4 %, inlined in the store db for small files) |
  | Receiver, peak | 2 | 1 per in-flight frame (store-owned until the export renames it) |
  | Receiver, steady, same volume | 1 | **1** |
  | Receiver, steady, root on another volume | 2 | **1** (the store is on the root's volume) |

  Each store's `blobs.db` is a preallocated 1 MiB redb file whatever it holds — measure a ledger as growth over the empty stores. The e2e asserts: A's working dir + collab store grow < 1 % of the published bytes; B's collab root grows by the payload + < 1 %; no file under B's working dir above 64 KiB other than the untouched store database.
- **Publish (§5.2, P2–P7, P18, P19, R3, R8–R10).** Gate per frame (the export-readiness verdict P7, the dictionary filter P3 — trimmed `FILTER` matched case-insensitively against `canonical` + `aliases`, the frame uuid P18), generate (`CalibratedLightOptions::default()`, OSC as CFA float FITS, P6; a plate solve's WCS replaces the header's, P4), seed by reference, announce in batches of ≤ 500, holder delta `add`. The recipe hash is the resolved masters + the source `size:mtime` — NOT the engine version (R3): an engine change needs the manual `republish_collab_frames`; a regeneration with identical bytes stores only the new recipe (no `…/version`). A new version lands over the same path. A hub "already announced" 409 adopts the frame and retries the rest (R8); the compute permit is taken only when something must be generated (R9); write-backs are column-targeted (R10). Auto-publish (R16, `collab_projects.auto_publish` default on): scan / analysis / plate-solve completion, frame-set linking, master build or rebuild and calibration-link changes mark projects dirty; one coalesced run per project after a 30 s debounce. **One publish run per project at a time** (final review C1, owner decision 2026-09-24): a per-project lock shared by publish, republish and auto-publish; a manual publish or republish while a run holds it is REFUSED at once (`Conflict("publication of this project is already running")`, shown in ProjectDetail as "Publication already running"), never queued; the auto-publish worker re-dirties the project instead. Two overlapping runs once posted the same bytes as two versions and every receiver deleted its replica. Before seeding an update the own row is re-read and before `…/version` again — a BLAKE3 equal to the row's CURRENT one is never posted (C1c). An update's rename → seed → own-row write runs under the project's disk lock, and the row's file columns are written right after the seed (`stage_own_file`; the unchanged recipe marks the version unconfirmed), so disk truth never counts the regenerated file missing; a refused version puts the hub's content keys back and marks the file not held (`unstage_own_file`, I2). New frames are checked against the hub's per-frame rules before calibration (EXPTIME in (0, 86400], filter 1..=80 bytes, channel, `meta` ≤ 8192 bytes; M1) — one bad frame would refuse the whole atomic batch — and every update and adoption target is reserved before a new frame picks its name (I1). A collab store that cannot be mounted refuses the publish before anything is generated (I3).
- **Version poll — retired (wave 3, L3).** The 15 s `GET /me/project-versions` loop is gone: project changes arrive on the event stream, and the stream's 60 s `versions` state vector plus the `prev`-checked catch-up replace it. What stays: a moved project gets `refresh_projects_reporting` (thresholds/dictionary moves fire the auto-publish hook, R11) and a manifest delta sync (cursor = highest applied `manifestVersion`, follow `next`; a caps or coordinator change resets the cursor to 0 and prunes, P9).
- **Replication — the live scheduler since wave 3.** The pass (per-frame holder lookups, `fetch_blobs_assigned` batches) is retired; the live runtime's scheduler fetches instead (next section). What stays: the local **policy** (`filters` canonical, `publishers`, `maxFwhmArcsec`, `minStars`, `byteBudget` counting what is held; `set_collab_policy` returns a preview; a narrowed policy never deletes) decides which frames are `wanted`; the collab lane takes ONE **collab-class** `ReceiveGate` permit (not one per batch), which it yields to a waiting personal transfer; one frame's failure never aborts its siblings; landing is conditional on the row's `content_version` + `blake3` still matching (R20); a target file that already holds the frame's content is linked, never exported over (C1b); nothing is fetched while the collab store is unmounted (I3); a received frame is immediately a seed.
- **Maintenance — retired (wave 3).** The 20-minute loop is gone. Disk truth is the storage engine's job now (watcher + settle + canary + stat sweep, per-frame local states); the full holder report is replaced by claims + outbox + digest (a full report only on a digest mismatch, an epoch change or a refusal); the hub's 75-minute holder freshness is replaced by presence. What stays: while the collab store is unmounted NO claim is reported and nothing is served — a device that cannot serve must not claim holds (I3); a present, hash-matching frame that lost its seed tag is seeded again (`ensure_seeded`); a frame tagged at another version (a publish moving it) is left alone (I2).
- **Loss guard — retired (wave 3, L4).** The fraction/bytes guard, its pause, its event and its command are gone, and its two settings rows are deleted at init (P33). Its replacement is the L4 deletion window (next section): ≤ 10 deletions in a rolling 5 minutes are re-fetched after the settle, more raise ONE non-blocking, reversible choice. `collab_projects.replication_paused` stays in the schema, unread.
- **Dead entries wait for GC (P20).** iroh-blobs 0.103 has no blob delete and a re-fetch over a vanished external file panics: a `Complete` entry whose first-byte probe fails parks the frame (`awaiting_gc = 1`, tags dropped, never a `Copy` repair) until `status(hash)` is `NotFound`; then the need set takes it again. Since wave 3 the collab GC runs every 60 s and the live runtime's GC probe re-checks parked rows at the same interval, so a single deleted replica comes back within the settle plus about a minute (P31).
- **Edited replica — quarantined since wave 3 (L5).** R24's rename-aside is superseded: a replica edited in place is `quarantined` at once (it stops serving), listed under Changed files, and nothing — not even a new version — ever lands over it until the user resolves it (refetch the original, the edit going to the Trash, or delete). Byte-identical frames share one store entry and are linked from the sibling's landed path (P24).
- **Lost projects (R14).** A project `/me/projects` no longer lists gets `collab_projects.lost_at`: its replica rows are deleted and unseeded (with its claims and outbox), own rows and files stay, it is hidden from cards and the live exchange, and every action path reads it through `live_project` (NotFound). A re-join clears `lost_at`.
- **Moderation (R27, R28).** `approve_collab_frame(…, trust)` returns nothing and logs the hub's `published` count (a trust approval publishes all that publisher's pending frames); `reject_collab_frame` does no local unseed. Both run a best-effort manifest sync: once the hub took the decision the command succeeds, a failed sync is a `warn!` for the next project event to repair (M9).
- **Project WBPP export (R31 — owner to confirm).** `export_project_for_wbpp` takes published ∧ accepted ∧ on disk ∧ not awaiting GC from `project_frames_local`; a contributor's own pending or rejected frames are not in it.
- **Compatibility (§11, P17, P12).** A hub `409 {"error":"collab_api_outdated"}` is `ApiError::Conflict(COLLAB_API_OUTDATED_MSG)`; the frontend matches the `collab_api_outdated` prefix and shows "Update required". The retired `Msg::AnnounceProject`/`RequestProject` stay in the frozen wire; the receiver drops them with a `warn!`. The package tables and dirs are gone (task 12).
- **Events** (UI data, not logs): `collab-published`, `collab-frames-changed`, `collab-frames-landed` (wave 3 adds five, next section; the wave-2 pause event is gone); one app-root hook (`useCollabNotifications`) turns them into notifications (R29), with NO content-shaped `dedupeKey` — the dedupe set persists in localStorage, and a content-shaped key would swallow a later genuine outcome with the same numbers forever (I4). New log fields are in the logging spec's dictionary (collab v3 wave 2 entry).

## Collab v3 — live exchange (wave 3, 2026-09-25)

Spec `docs/superpowers/specs/2026-09-25-collab-v3-live-exchange-design.md` (invariants I1–I11, owner rulings L1–L12) and amendments A5/A6 of `2026-09-23-collab-v3-per-frame-model-design.md` §16; plan `docs/superpowers/plans/2026-09-25-collab-v3-wave3-app-live-exchange-plan.md` (P1–P33), controller rulings in its SDD ledger. The app follows the hub live instead of polling it: one event stream per device, claims reported through an outbox, a deterministic scheduler, a serve check on every request and a per-frame local state machine. Code: `api/collab_live/` (`runtime`, `session`, `workers` — the ordered feed worker and the storage task —, `feed`, `holdings`, `executor`, `landing`, `replace`, `storage_task`, `serve_oracle`, `surface`), `collab/live/` (wire, stream, presence, holders, outbox, digest, back-off), `collab/scheduler/core.rs`, `collab/storage/` (marker, watch, sweep, states, deletions), `sharing/iroh/collab_pool.rs`, `db/collab_live.rs`, `sync/receiver.rs` (the two-class `ReceiveGate`). In-process proof: `api/collab_live/live_tests.rs` and `api/collab_v3_live_e2e_tests.rs` (three instances, the spec §12 latency table, A5, A6, the disk ledger).

- **Event channel (§4.1, §4.3, §4.4).** One SSE stream per device, `GET /me/events` over a dedicated streaming client (50 s read timeout = 2.5 × the hub's 20 s keepalive; full-jitter reconnect 1 s → 60 s; `unreachable` after three failures). The first event is `hello` (session id, epoch, per-project `version`/`holderSeq`/claim count/digest/`reportSeq`, presence); the others are `project`, `holders`, `presence`, `members`, `resync`, `account` and the 60 s `versions` state vector. Every delta names its `prev`; a gap catches up over REST from the stored cursor, a cursor the hub cannot serve reloads the snapshot. An epoch change (a restored hub, or a stored cursor ahead of `hello`) reloads every project, reconciles the holdings and re-announces this device's own frames the hub lost under their uuids (Task 18 found and fixed a holding lost there: a claim refused before the re-announce is now reported again when the frame is listed anew). Events apply in stream order on ONE feed worker; hub HTTP never runs on the runtime's loop (Task 15 C1), nor does a catalog write (final fix A-I2: the replication-scope re-derive, a fetch's error record and the GC release run on blocking threads; a re-derive that fails is retried after its back-off, never dropped), and the session id comes from the pump, never through the event queue. The re-announce check owed when the publishing binding moves here ("Publish from this device", or a refresh that shows it) runs on the feed worker too, so the command returns at once; only with no live exchange running does the command run it itself, `Interactive` (A-I1). A worker that dies restarts the whole runtime, and nothing is advertised as served meanwhile (A-I3); a stop is answered while the runtime starts or its stream opens (A-M2); Sync now and the other commands sent before a runtime runs are queued for it (A-M4); a stopping runtime replaces the serve oracle only while it is still its own (A-M1); a fetch prepared just after its run ended at a yield is cancelled with the run's other items, never struck (A-M3).
- **Presence (§4.2, P28).** A beat every 15 s and on every change of the serving map or the home relay, carrying the session id; the hub's rules (40 s of silence, 10 s grace after a closed stream) take a device offline, the app only shows them. A clean exit or sign-out sends `DELETE /me/presence` (bounded 2 s; the whole stop fits `STOP_BOUND` = 3 s, its waits run at once). `409 session_gone` reopens the stream; a wall-clock jump past the monotonic clock (a wake from sleep) reconnects — there is no sleep hook on desktop (P28). Presence only adds provider candidates; an in-flight transfer ends only with its connection (I5).
- **Holdings (§6).** The hub's holder map is persisted per project (`collab_holders`, cursor `holder_seq`, delta resume). This device's claims (`collab_my_claims`) change ONLY with its local state, in the same transaction, through the outbox (`collab_outbox`), flushed after `nextFlushMs` (default 1 s) or at 500 entries, stamped with one per-device `report_seq`. Every report carries the claim-set digest (vectors pinned against the hub); a mismatch sends one full report; an hourly digest check runs off the critical path. The hub keeps an announce's or a version's implicit claim through a full report that does not name it (hub 06198cc), so a full report that still answers `digestMatch: false` is followed by a second one that lists under `remove` every frame this device's own holder-map row carries and its claim set does not — never a frame with an announce or version call in flight; a difference left after that is `info!` when such a call or a claim the report raced explains it, `warn!` otherwise (final fix D-18/D-19). An announce or a version is an implicit claim (added locally without a report). A claim the hub refuses (a frame it does not list, or not at that version) is dropped and its row marked; the next manifest row for that frame re-reports it.
- **Scheduler (§7).** A pure, deterministic core (`collab/scheduler/core.rs`, seeded simulation of 300 seeds × 400 steps) owns the need set (`wanted` rows only), the per-version provider lists (claimed at the current version ∩ online and serving), the order — rarest first, then random, a frame waiting over 1 h jumps the queue —, one frame per work unit (capped at 256 MiB), fetch ids, per-frame and per-provider back-off, and every cancel: a new version, an exclusion, a lost project, a membership change, a policy change, auto-replicate off and storage loss cancel at once (§7.4). Providerless frames sleep and cost nothing. The executor carries out its commands over the live assignment run and lands what it fetched.
- **Transport (§7.3, §8, §9.3).** One connection per provider through the collab pool (10 s connect, 30 s QUIC idle / 5 s keep-alive, kept 60 s after its last request, dial back-off 1 s → 60 s). The provider answers every get through its serve check: only a `held`/`own_held` row of the CURRENT version whose file still matches its `size:mtime` stamp is served (`ERR_PERMISSION` otherwise, and a stamp mismatch queues an immediate local check); past the upload stream limit a get is refused with `ERR_LIMIT` and the fetcher tries another provider; an inbound push is always refused. After every membership refresh the connections of devices the connect gate no longer admits are closed (I11). Stream limits: `collab.max_upload_streams` (1..=64) and `collab.max_receive_streams` (1..=32), both 8 until the owner-run relay measurement picks them (P21), live on both hosts (Settings → Transfers). The upload pacer is class-aware: while a personal upload runs, collab throttle replies are held to a low share of the link.
- **Priority (§8, L1, P18).** The `ReceiveGate` has two classes. The collab exchange holds at most ONE collab-class permit (one lane); while a personal transfer waits, no new collab unit starts and each running one finishes only its in-flight frame, so a personal transfer waits at most the frames in flight — the e2e derives its bound from units in flight × frame size at the upload rate. The personal side is unchanged (one permit per package).
- **Local storage (§9).** The Collaboration root carries a store marker (`.athenaeum/store-id`, recorded in the catalog; every adoption decided under one lock) — a root marked by another device is refused, never taken silently. A watcher (10 s aggregation, 60 s settle for deletions, a canary every 5 min) and a stat sweep (hourly ±25 %; every 5 min when the watcher is dead or the volume is a network one; 2 s mtime tolerance) feed the per-frame state machine: `wanted`, `held`, `idle`, `quarantined`, `awaiting_choice`, `not_kept`, `missing`, `own_held`, `own_missing`, `own_changed`. L4: a deleted replica is re-fetched after the settle when ≤ 10 were deleted in the rolling 5 minutes; more raise ONE non-blocking, reversible choice (Refetch / Stop keeping) that counts every deletion in the window; a second deletion within 24 h joins the choice; a frame with fewer than 2 other holders of its version gets the last-copy warning, and one nobody else holds a "lost everywhere" notice. L5: an edited replica is quarantined at once. L6: "Keep again" undoes Stop keeping. A move inside the root is re-adopted by hash, never counted as a deletion. An unavailable store (path missing, not a directory, marker missing or foreign) changes no frame state; serving goes false in the next beat and comes back on the remount with nothing fetched again.
- **A5 — the Collaboration folder re-designated.** A mount change restarts the live runtime on the new root (it waits for the new marker to be recorded). Held replicas outside the current root are first re-adopted by hash from the new root: a MOVED or COPIED folder (its store too) brings every file along, so nothing is fetched again, no choice is raised and no `_1` duplicate is written (final fix B-I1). Only a replica with no matching file in the new root counts as gone and goes through L4 (≤ 10 re-fetched into the new root, more raise the choice); the files in the old folder stay where they are, and a "lost everywhere" notice names the previous folder instead of the Trash. Own frames never count. A frame the scanner found moved while no engine ran gets its path repaired and its stamp cleared, and the engine re-checks its seed (re-seeded, or parked over a dead store entry — B-M4). A publish regenerates into `<target>.athpub`, never the landing temp's `.athtmp` that the session sweeps at its start (B-M2); a quarantined replica that turns own becomes `own_changed` and its quarantine record goes (B-M1).
- **Device replace and take-over (§9.5, L9).** A root whose marker names another device of the account offers "replace that device" (prompted after 7 days offline, retirement proposed after 30, never automatic): `collab_replace_device` checks every local precondition BEFORE the hub retire, records the replaced device (A6: its frames stay this device's own), rewrites the marker, designates and re-adopts the files by hash — every step after the retire is retryable. A marker naming a device the account does not list is taken over only by the explicit, confirmed `take_over_collab_folder` (no hub call). The status read is passive; "Check again" (`check_collab_folder_owner`) asks the hub and stamps `checkedAt`.
- **A6 — one publishing device per account per project.** The hub binds the first device that publishes; an announce from another device of the account is refused (`collab_publishing_device:<name>`), and a version only from the frame's own device (`NotPublishingDevice`). `own` is derived per DEVICE from the manifest's `publisherDeviceId`, so a second device of a `send_receive` account receives, holds and serves its account's frames as replicas (a `send` account's devices store nothing). "Publish from this device" (`set_collab_publishing_device`) moves the binding and re-announces what the hub lost meanwhile; new file names are unique against the publisher's whole manifest.
- **Landing (§7.5, P12, T11).** An owned blob lands by the store's own export straight onto the target (an atomic rename, pinned by a canary test); an inline, external or cross-volume one lands through a `.athtmp` temp, BLAKE3-checked, renamed over the target and re-imported by reference — never a delete-first, never over a quarantined file, orphaned temps swept at mount. A version bump that replaced a file a sibling frame's content was read from parks the sibling until the GC, then re-adopts it from its own file (no second copy).
- **Commands (both hosts).** `collab_sync_now` (Sync now: reconnect, clear every back-off, reconcile), `get_collab_live_status` (polled; `debug` span), `list_collab_attention` (Changed files, Not kept, Other files, awaiting choice), `resolve_collab_deletions`, `preview_collab_stop_keeping`, `keep_collab_frames_again`, `resolve_collab_changed_file`, `get_collab_storage_status`, `check_collab_folder_owner`, `collab_replace_device`, `take_over_collab_folder`, `set_collab_max_upload_streams`, `set_collab_max_receive_streams`, `set_collab_publishing_device`; `list_collab_frames` reads the live holder counts.
- **Events.** `collab-live-status`, `collab-deletion-choice` (per-occurrence `dedupeKey` with a batch id), `collab-frame-lost` (with the previous folder under A5), `collab-frame-changed`, `collab-attention-changed`; `useCollabNotifications` turns the discrete ones into notifications.
- **Retired by this wave.** The version poll, the 20-minute replication pass, the maintenance loop, the loss guard and its settings (P33), the per-frame holder lookups, the full holder chunks, `fetch_blobs_assigned`, and three commands on both hosts — the frames refresh, the per-project "sync now" and the loss resolution (Sync now and the attention lists replace them).
- **Acceptance.** In process (the e2e, relay disabled): every §12 bound holds with a wide margin (A publishes → B starts fetching in ≤ 8 ms against 2 s; C fetches from B 0.7–0.8 s after B lands against 3 s; a clean exit is seen in ≤ 12 ms against 2 s; a killed device is dropped 10.1 s after its last beat against 50 s; a single delete is back in 1.2–1.7 s; a personal transfer waited 1.9 s against a derived 5 s), and the disk ledger shows exactly one copy per frame on every instance, the collab store grown by < 0.4 % of the payload and the working dirs by 0 B. Owed: the same on the real test hub and test relay, the relay stream measurement, the desktop click-through and a one-week soak (`docs/superpowers/open-items.md`).
