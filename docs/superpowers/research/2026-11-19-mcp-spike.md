# MCP spike — what the clients actually do (2026-11-19)

For the MCP design (`docs/superpowers/specs/2026-10-27-athenaeum-mcp-design.md`, §11). A throwaway server
(`rmcp` 3.11.0 behind a plain stdio ↔ Unix-socket byte pipe, the way `athenaeum-mcp` will reach the app) logged every
message while the real clients used it. The spike code and logs were deleted at its close; this note keeps the facts.

## The probe

- `spike_plan` (model-visible, linked to a `ui://` view): a fake plan of three duplicate groups; text `content`,
  `structuredContent` with a marker, result `_meta` with another marker and a token.
- `spike_apply`, `spike_view_token` (app-only, `_meta.ui.visibility: ["app"]`): the view fetches its own token and
  applies with it.
- `spike_elicit` (model-visible): a form with a boolean, one choice and a multi-select; legacy server request on
  2025-11-25, an "input required" result (MRTR) on 2026-07-28.
- The view: one self-contained HTML (official MCP Apps client SDK `@modelcontextprotocol/ext-apps` 2.0.4, 607 KB),
  showing what reached it.

## Measured

| | Claude desktop 6.6395.1 (macOS) | Claude Code 2.1.328 (terminal) |
| ---- | ---- | ---- |
| Revision | 2025-11-25 with `initialize`; two connections: `claude-ai` (view, resource reads) and `local-agent-mode-<server>` (the model's calls) | 2026-07-28 stateless: `server/discover`, capabilities in each request's `_meta` |
| Declares | `extensions["io.modelcontextprotocol/ui"]`, no elicitation | `elicitation {form, url}`, `extensions["io.modelcontextprotocol/tasks"]`, no UI |
| View | read when the tools loaded, drawn in a side pane with the client's theme and colour variables; the view's own app-only calls (token, five applies) reached the host | none |
| Form | — | drawn in the terminal; the owner's answer (`accept`, boolean, one choice, three of three groups) reached the host; `-p` sessions answer `cancel` by themselves |
| App-only tools and the model | not in the model's list; asked to call `spike_apply` itself, the model tried the client's "App view tool list" route, it failed, nothing reached the host | not in the model's list ("no spike_apply tool") |
| What the model read | `content` only (no `structuredContent` marker, no `_meta`) | `structuredContent` as JSON instead of `content`; no `_meta` |
| What the view got | `structuredContent` yes, result `_meta` no | — |

A plan created on the model's connection was applied from the view on the other connection.

Not measured: the first message of a new chat in Claude desktop (reported below), the desktop Code tab, Windows,
Linux, claude.ai web (remote connectors only; out of scope for a local app).

## From the documentation (not re-measured)

- MCP Apps spec 2026-01-26 (stable): tool `_meta.ui.resourceUri`, resource MIME `text/html;profile=mcp-app`,
  `_meta.ui.visibility` ⊆ `["model", "app"]`; a host MUST NOT list a tool without `"model"` to the model and MUST
  refuse a view's call to a tool without `"app"`; the view's CSP denies network unless declared; hosts MAY prefetch and
  cache the view. github.com/modelcontextprotocol/ext-apps, `specification/2026-01-26/apps.mdx`.
- No wire field tells a view's call from the model's (ext-apps issue #746).
- Claude desktop renders MCP Apps for local stdio servers (claude.com/docs/connectors/building/mcp-apps/getting-started);
  Claude Code's terminal does not (…/mcp-apps/quickstart).
- Reported Claude desktop bugs: no view on a chat's first turn while the extension is still declared
  (anthropics/claude-code#108122, anthropics/claude-ai-mcp#1243); tool result delivered to the view without
  `structuredContent` (modelcontextprotocol/ext-apps#696, anthropics/claude-code#103809); result `_meta` lost on reload
  (anthropics/claude-code#99677); elicitation declared but never drawn in older builds (anthropics/claude-ai-mcp#1085)
  — the measured build no longer declares it.
- Elicitation (spec 2025-11-25 and 2026-07-28): form schema is flat primitives — string, number, boolean, one enum,
  a multi-select array of enum; accept / decline / cancel; no secrets in forms. Claude Code since 2.1.76, with
  `Elicitation` / `ElicitationResult` hooks; Esc answers later (2.1.324). code.claude.com/docs/en/mcp.
- `rmcp` 3.11.0 (2026-11-17): both revisions; `Tool.meta`, `CallToolResult { content, structured_content, meta }`,
  custom resource MIME; elicitation behind feature `elicitation` (`create_elicitation_with_timeout` on 2025-11-25,
  `InputRequiredResult` on 2026-07-28, chosen by `RequestContext::protocol_version()`; capabilities through
  `RequestContext::client_capabilities()`, which reads the stateless `_meta` too); any `AsyncRead + AsyncWrite` is a
  transport. No MCP Apps helper (rust-sdk#891).

## What the design takes from it

No in-chat way works in every client (the view only in Claude desktop, the form only in Claude Code), so the owner
ruled on 2026-11-19 that v1 confirms every plan in Athenaeum's own window, in every client (spec §6.4, §11). Kept
from the spike for v1: both halves of a result read on their own (§6.1); two protocol revisions, several connections
per client and app-wide plans (§6.4, §7); a plain byte-pipe bridge (§7). Kept for a later in-chat plan card (§12):
the card fetches its plan by handle and gets a one-time token that way; app-only tools only on a connection that
declared MCP Apps; the card registers no tools; Claude desktop's first-message and lost-`_meta` bugs.
