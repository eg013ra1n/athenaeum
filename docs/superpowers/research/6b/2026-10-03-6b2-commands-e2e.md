### 2.2 The change (spec §9.2) and a recommended form

Spec: on the two events, `setId` becomes optional and `projectId` (optional) is added; exactly one is set. Spec §7 says the plan carries
"`subject`". Recommendation: **one convention on all four wire types**, the flat pair, so 6c keys every map one way
(`setId != null ? 'set:'+setId : 'project:'+projectId`):

```rust
// one helper replaces wire_set_id
pub(crate) fn wire_subject(subject: &StackSubject) -> (Option<i64>, Option<String>) {
    (subject.frame_set_id(), subject.project_id().map(str::to_string))
}
// events / RunSummary / StackingPlan:   pub set_id: Option<i64>, pub project_id: Option<String>
// StackingRunRow: pub frames_set_id: Option<i64>, pub project_id: Option<String>  (drop #[serde(skip)]/#[ts(skip)])
```

`FanOutTicker` should hold a cloned `StackSubject` (or the pair), and the tick helpers should take `&StackSubject`. Field comments must be `//`
not `///` (README rule: ts-rs copies `///` into `src/types`). `project_id` on `StackingRunRow` has a `///` today (db/stacking.rs:104)
that would leak once un-skipped. ts-rs output: `setId: number | null, projectId: string | null` (both required keys,
`#[serde(default)]` doesn't make them optional, see `mastersBuilt`). If the plan also gets a ts-exported `StackSubject`
(externally tagged, `{frameSet:n} | {project:s}`), that's a second keying rule. I'd not do it.

### 3.3 The namespace overlap and a safe layout

- A frame set named `projects` (or `Projects` on case-insensitive APFS/NTFS) has its root **at** `<working>/projects`. Its `cleanup_work`
  `remove_dir_all`s `<working>/projects/{registered,calibrated,ln,fits,rej,runs,previews}`. A project whose hub slug is one of those words
  (hub `slugify` = lowercase ascii-alnum + `-`, `athenaeum-hub/src/routes/projects.rs:44-65`; e.g. a title "Registered") has its whole tree
  there, so it gets deleted. Its `calibrated_bytes` also count the project's tree. The reverse direction is benign.
- Separately, stacking folder overlap with scan roots is only a **warning** (`OverlapRule::Warn`, paths.rs ~357-394), and the Collaboration root
  is a `scan_roots` row (`kind='collaboration'`, scan_roots.rs:85). Landings go to `<Collab>/<project folder>/<publisher folder>/<file>`
  (`api/collab_live/landing.rs:273-293`). If working = parent of a Collaboration root that is itself named `projects`, then
  `<working>/projects/<slug>` **is** `<Collab>/<slug>`. A publisher whose display folder is `Registered`/`Calibrated`/`Runs`/… would have
  its landed replicas deleted by `cleanup_project_stacking_work`. It's a corner case, but it's data loss.

Proposed layout and guard:
- `<working>/_projects/<set_slug(slug)>/…`. `set_slug` = `sanitize_for_filename` (`archive/path_layout.rs:8-25`), which `trim_matches('_')`s
  after all substitutions. `windows_safe_component` only ever appends (`CON` → `CON_`). So **no frame-set slug can start with `_`**, under either case
  rule. Pin it with a property test over adversarial names. Hub slugs are unique, lowercase, `[a-z0-9-]` ≤ 60, and set at creation
  (no update route in the hub), so project roots never collide with each other. Optional extra: a `-<first 8 of project_id>` suffix, against two
  hubs' projects sharing one DB. Zero migration: no project tree has ever been written (6b-1 refuses every project entry point).
  This deviates from spec §9.3's `projects/` wording and needs the owner's nod; update paths.rs:1888 and run.rs:19970.
- **A `folders` blocker** in the project plan when the project layout root and the Collaboration root (`get_collaboration_dir`) overlap in either
  direction. `cleanup_project_stacking_work` re-checks and refuses (`Invalid`). This closes the landed-replica path whatever the
  folder names are.

## 4. ComputeQueue label and the notification link

- **Label: no new code.** `run.rs:1262` `format!("Stacking · {}", rc.set_name)`; `rc.set_name = plan.set_name`; `build_plan` sets
  `set_name = subject_label(conn, subject)?` (plan.rs:1683). `subject_label` already returns `collab_projects.title` for a project
  (plan.rs:850-865). Once the project plan fills `set_name` from `subject_label`, the label is `"Stacking · <title>"`. Pin it with a test:
  hold the queue (`ctx.compute_queue.acquire(ComputeJobKind::Analysis, "hold", flag)`, the pattern at run.rs:10141), start a project run, and assert
  `ctx.compute_queue.snapshot()` (compute_queue.rs:156) has that label. The frontend `ComputeQueueIndicator.tsx` only displays labels and parses
  nothing. Side effect: masters are named `master_file_name(set_name=title, …)` (master_cards.rs:377).
- **Notification link: core emits only `projectId`** on `stacking-complete`. 6c builds `` `/projects/${projectId}?tab=stacking` `` in
  `useStackingRuns` and must add `'stacking'` to `ProjectDetail.tsx`'s `Tab` union and `TAB_ALIASES` (43-71). Today
  `resolveTab('stacking')` returns `null`, so the link would fall back to the default tab. Until 6c the guard drops project events, so no notification
  appears. That's acceptable because no UI can start a project run before 6c.

### 5.3 Producing landed files
