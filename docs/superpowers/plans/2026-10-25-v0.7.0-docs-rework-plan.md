## 2. Style rules (every page)

- **Short.** A guide is 300–800 words; Settings and Stacking may reach 1000. Today's 32 000 words across
  the guides should land near 12 000.
- **Task-first.** Sections are "How to …" with numbered steps naming the exact control as spelled in the
  UI (bold). Concepts get one paragraph, only where a step needs them.
- **One worked example per guide** — a real process with real-looking values ("Ha, 40 × 300 s, ASI2600MM,
  -10 °C → …"), as a short numbered walk-through.
- **No history.** No "since v0.5.5", no "new in", no release narrative; that is the blog's job.
- **No internals.** No table names, command names, algorithm derivations or file formats beyond what a user
  touches (`.athln` is fine where a user sees it on disk). Never name another program.
- **Tables only for reference** (match modes, settings fields), never for prose.
- Each screenshot is one idea, cropped to the region that matters, with at most two highlights.
- English, US spelling as the site uses today; the UI's own capitalisation.

## 4. Writing

Pages are independent files, so they are written in parallel by sub-agents, one group per agent
(Library; Quality and calibration; Processing; Sharing; Getting Started + Housekeeping + Settings). Each
agent reads the old page, the matching reference under `docs/`, and the React code for exact labels
(`src/pages/`, `src/components/`, `src/settings/registry.ts`), writes its pages, and marks every image as
`<!-- shot: <guide>/<name> — what it shows, what to highlight -->` where it belongs. The controller reviews
every page against §2 (length, steps, example, no history) before the screenshot pass.

## 5. Screenshots

- **Source:** the release `athenaeum-web` binary + `npm run build:web` served by it, on a COPY of the dev
  catalog (`~/Library/Application Support/com.vsharifov.athenaeum.dev/athenaeum.db`, 545 MB) in a scratch
  dir on the data disk (not the session scratchpad). FITS files are read in place, read-only; nothing that
  writes to files is clicked.
- **Hub safety:** the copy carries the dev device's identity. Before it goes live, sign the copy out of
  the hub or block its live runtime, so it never takes over the dev device's publishing role or presence on
  the test hub. Collab screens then come from the desktop dev app on the test hub, or from a dedicated
  second test account signed in on the copy — decided when that pass starts.
- **Capture:** `puppeteer-core` driving the installed Google Chrome, headless, viewport 1440 × 900 at
  device scale 2, dark theme (and light where a page shows both). A script in `artfrom-space/scripts/`
  (`capture-shots.mjs`) lists each shot as route + actions + crop selector, writes the raw PNG, and
  `docs-shots.mjs` crops and highlights as today. Retaking all shots is one command.
- The six landing shots (`src/assets/screenshots/`) are retaken in the same run.
