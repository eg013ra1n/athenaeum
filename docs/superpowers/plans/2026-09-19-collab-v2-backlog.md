**Источники решений:** прототип портала `athenaeum-hub/docs/design/2026-09-19-portal-v2-prototype.html` · жизненный цикл `athenaeum-hub/docs/design/2026-09-19-collab-lifecycle-4-members.md` · D4 `docs/superpowers/specs/2026-09-19-swarm-fast-paths-design.md` · предшественники: BRD, Stage II design, D1–D3

Документы — источник «почему». Этот файл — источник «что и в каком порядке». Каждая задача размером с ветку: одна задача, один PR, свои тесты.

**Оценки:** S — до дня, понятная правка в одном месте. M — 2–4 дня, затрагивает схему или несколько слоёв. L — неделя+, новая подсистема или новая машинерия на проводе.

---

## Инварианты, которые нельзя нарушить ни одной задачей

Эти три правила ломаются молча и дорого. Каждая задача, трогающая соответствующий слой, обязана иметь тест, падающий при нарушении.

1. **Governance-флаги никогда не попадают в подписанный снапшот членства.** В снапшоте живут только `dataRole` и `coordinator`. Делегирование модерации не меняет ничего на проводе. Тест: снапшот проекта, где у участника выданы все governance-флаги, побайтово равен снапшоту, где не выдано ни одного.
2. **Клиент применяет каждый проверенный по подписи снапшот целиком, сравнивая содержимое, а не версию.** `membershipVersion` не растёт при добавлении и отзыве устройства. Кэш, ключованный по версии, оставит отозванное устройство авторизованным.
3. **Присутствие и любые данные, пришедшие от пира, — подсказка, никогда не источник авторизации.** Авторитетен только хаб.

### H1 — Плоскость governance

Роль данных (`send` / `send_receive`) остаётся как есть и остаётся единственным, что едет в снапшот. Управление — отдельный набор флагов, хранится и проверяется только хабом.

Флаги: `members.manage`, `data.moderate`, `project.edit`, `thresholds.edit`, `invites.manage`, `posts.write`. Пресеты для UI: Member (пусто), Moderator (`data.moderate` + `posts.write`), Co-coordinator (все шесть). Координатор — не пресет, а владение: все флаги плюс передача и удаление проекта.

Схема: `project_members.gov_caps text[] NOT NULL DEFAULT '{}'`. Миграция проставляет координатору все шесть.

Все места, где сейчас стоит проверка `is_coordinator`, переводятся на проверку конкретного флага; `is_coordinator` остаётся только там, где речь о владении. Новый эндпоинт `PATCH /projects/{id}/members/{account_id}` принимает и `dataRole`, и `govCaps`.

**Приёмка:** участник с `data.moderate` может одобрить пакет и не может менять пороги; снапшот не меняется от выдачи флагов (инвариант 1); попытка выдать флаги самому себе без `members.manage` — 403.

### H2 — Бывшие участники

Сейчас после ухода `LEFT JOIN project_members` не находит строку, код подставляет `"former member"`, и — главное — `per_member` агрегируется в `HashMap` по **отображаемому имени**, так что все ушедшие схлопываются в одну строку с суммарными часами.

Схема: `project_alumni (project_id, account_id, display_name, data_role, joined_at, left_at, how text CHECK (how IN ('left','removed')), credited bool DEFAULT true)`. Заполняется в момент ухода и удаления участника.

Агрегация прогресса переводится на ключ `account_id`, имя резолвится через `project_members ∪ project_alumni`. Публичная страница получает блок past contributors. Флаг `credited = false` заменяет имя на «бывший участник», не трогая цифры.

**Приёмка:** двое ушедших с разным вкладом дают две строки, а не одну; их пакеты сохраняют авторство на публичной странице; повторное вступление переносит строку обратно в участники, не теряя истории.

### H3 — Have-report как мягкое состояние

`PUT /projects/{id}/have` с телом `{ "packageIds": [...] }` — полное множество того, что устройство держит по проекту. Апсерт с `ON CONFLICT DO UPDATE SET reported_at = now()`, строки этого устройства вне присланного множества удаляются. Старый `POST /announcements/{id}/have` остаётся для мгновенного сигнала после ингеста.

Счёт холдеров получает условие свежести `reported_at > now() - interval '75 minutes'`. Отдельно: издатель подмешивается в холдеры (`have_reports ∪ {publisher}`) — иначе у контрибьютора с ролью `send`, который физически не может отчитаться, свежий пакет показывается как потерянный.

**Приёмка:** отчёт с сокращённым множеством уменьшает счётчик; отчёт старше окна не считается; свежеопубликованный пакет контрибьютора показывает одного холдера, а не ноль.

### H4 — Дверь проекта

`projects.join_policy text CHECK (join_policy IN ('open','request','invite')) DEFAULT 'request'` и `projects.default_data_role`. При `open` эндпоинт заявки создаёт участника сразу (после принятия правил дома на клиенте); при `invite` — 403 с понятной причиной.

**Приёмка:** смена политики не трогает существующих участников; при `invite` публичная страница отдаёт проект, но без возможности подать заявку.

### H5 — Инвайт-ссылки

`project_invites (id, project_id, token, grants_data_role, max_uses, used_count, expires_at, revoked_at, created_by)`. Токен — 16+ байт случайности, в URL. `POST /invites/{token}/redeem` создаёт участника с зашитой ролью, минуя очередь. Отзыв не трогает тех, кто уже воспользовался.

**Приёмка:** исчерпанная, просроченная и отозванная ссылки дают разные внятные ошибки; повторное использование одним аккаунтом не плодит вторую строку членства.

### H6 — Жизненный цикл заявки

Состояния: `open`, `asked` (вопрос задан, ждём заявителя), `approved`, `declined`, `withdrawn`, `stale` (без ответа 30 дней).

`join_request_messages (request_id, author_account_id, body, created_at)` — короткий приватный тред между заявителем и теми, у кого `members.manage`. `POST /join-requests/{id}/ask`, `POST /join-requests/{id}/reply`, `POST /join-requests/{id}/withdraw`. Отказ принимает `{reason, offerFollow, block}`; `block` пишется в `project_blocks`.

**Приёмка:** вопрос переводит заявку в `asked` и убирает её из счётчика «ждут меня»; ответ возвращает в `open`; заблокированный аккаунт получает 403 на новую заявку.

### H7 — Подписчики

`project_watchers (project_id, account_id, created_at)`. Подписка — **не членство**: не попадает в снапшот, не считается холдером, не появляется в списке участников. Эндпоинты follow/unfollow, счётчик на публичной странице.

**Приёмка:** подписчик не появляется в снапшоте ни при каких условиях (инвариант 1 по смыслу).

### H8 — Апдейты проекта

`project_posts (id, project_id, author_account_id, body, created_at)`. Право — `posts.write`. Последний апдейт уходит в OG-описание страницы проекта.

### H9 — Цели и фильтры каталога

`projects.goals` сейчас нетипизированный. Привести к `{filter: hours}` с валидацией. Считать «сколько не хватает» на стороне хаба и отдавать в каталоге. Параметры `GET /projects`: `?needs=OIII`, `?door=open`, `?status=active`, `?needsProcessors=true` (у проекта меньше трёх участников с ролью `send_receive`).

**Приёмка:** фильтр по фильтру возвращает только проекты с ненулевой нехваткой; сортировка по величине нехватки стабильна.

### H10 — Результаты

`project_results (id, project_id, url, title, author_display, published_at)`. Хаб хранит URL и подпись, изображений не хранит — превью тянет браузер читателя с чужого домена. Право — `project.edit`.

### H11 — Профили и история кандидата

Профиль на аккаунте: имя, локация, небо (Bortle), био, гир (текст), ссылки. Публичная страница `/api/v1/profiles/{handle}`.

Отдельно — агрегат для карточки заявки: в каких проектах состоит, суммарные часы и кадры, принятые против отклонённых пакетов, сколько пакетов держит сейчас, как стабильно онлайн. Всё уже выводимо из существующих таблиц; это один запрос, а не новое хранилище.

**Приёмка:** у аккаунта без истории агрегат отдаёт нули, а не ошибку; кандидат видит свой профиль ровно в том виде, в каком его видит координатор.

### H12 — Преемник

`projects.steward_account_id`, `projects.steward_after_days`. Фоновая задача переводит владение, если координатор не заходил дольше порога, и пишет событие. Уведомления обоим.

**Приёмка:** передача идемпотентна; преемник может отказаться до срабатывания.

### H13 — Почта

Письма: заявка получена (координатору), решение (заявителю), вопрос задан / отвечен, еженедельный дайджест всего, что ждёт дольше `median + 3` дней. Тема письма уже умеет нести префикс окружения.

### H14 — Оператор

Очередь жалоб на проект (кнопка «пожаловаться» на публичной странице → строка → оператор скрывает или отклоняет). Отдельная панель «координатор молчит N дней, заявок в очереди M». Обе вещи закрывают Q6 и Q7 из BRD.

### H15 — Подпись запросов ключом устройства

Решение владельца 2026-09-21. Сегодня хаб узнаёт устройство только по bearer-токену: украденный токен работает с любой машины, а поле `capability` устройство заявляет о себе само. Привязать токен к ed25519-ключу устройства (тому же, что уже лежит в `devices.pubkey` и подписывает членство): каждый запрос устройства несёт подпись `(method, path, body-hash, timestamp, nonce)` этим ключом в заголовке, хаб проверяет её по `pubkey` найденного по токену устройства, отвергает окно старше N минут и повторный nonce. Токен без ключа становится бесполезен, ключ не покидает машину. Это ограничивает украденные учётные данные, а не «чужую программу» — клиент отличить нельзя в принципе (секрет в открытом бинарнике), и это НЕ цель задачи. Портальная cookie-сессия остаётся как есть (браузер ключа не имеет). Мягкий ввод: хаб принимает и подписанные, и неподписанные запросы за переходный период, `devices.signing_required_from` включает строгий режим по устройству. Приложение: A12 — подписывать запросы `AccountClient` ключом iroh-узла; Perseus то же. Rate limit на OTP уже есть (5 запросов / 15 мин на e-mail и на IP, блокировка после серии неверных кодов) — не задача.

**P8.** Экран выхода: что остаётся проекту навсегда, у каких пакетов нет второго держателя (с кнопкой «попросить реплицировать»), что и где останавливается, что делать с чужими кадрами на диске (оставить / удалить — как выбор про место, не про права), галочка «оставить меня в кредитах». Координатор сначала передаёт проект.

**A2 — самая важная и единственная, которая про корректность.** Сегодня переключение на другого холдера происходит только по ошибке. Пир, который принял соединение и отдаёт 20 КБ/с, не отсекается ничем: ошибки нет, QUIC idle timeout не срабатывает, дочерний запрос занимает слот сколько угодно. Нужен свой цикл назначения поверх `store.remote()` (~150 строк) с дедлайном по прогрессу, хеджированием на отметке p95 и token-bucket на бюджет хеджей. **Путь отмены проигравшего обязан быть покрыт тестом** — иначе хеджи тихо удвоят исходящий трафик раздающих.

**A7 делать до A4.** В открытом iroh#4286 зафиксировано, что на LAN упор идёт в ~40 % канала на BBR и ~1.5 % на CUBIC. Если этот потолок у нас есть, оптимизировать выбор источника поверх него бессмысленно. Мы на iroh 1.0.3 / noq 1.1, доступны 1.2.0 / 1.3 — возможно, починено.

**A9.** Названия ролей в UI (Contributor / Processor вместо `send` / `send_receive`), состояние «у аккаунта ещё нет устройства», паритет экрана выхода с порталом, отображение держателей с подмешанным издателем.

## Открытые вопросы — нужны решения до соответствующих задач

1. **mDNS для кросс-аккаунтных пиров** (блокирует A10). Даёт LAN-скорость двум участникам в одной сети, но пересматривает правило S1 «наружу только relay_url» и решение D1 не строить кросс-аккаунтный сигнал присутствия. Внутри одного аккаунта включается без вопросов.
2. **Push от хаба вместо опроса.** По времени до первого байта даёт больше, чем вся волна 4. Требует своего дизайна: SSE, переживание разрывов, поведение при спящем клиенте.
3. **Удаление аккаунта.** Кадры уже в чужих стеках и не отзываются. Вероятный честный ответ — «имя убираем везде, кадры остаются обезличенными», но это надо записать до того, как кто-то спросит. Блокирует финальный текст правил дома.
4. **Q3 из BRD — шаблон текста правил дома.** Нужен для формы создания проекта (P5, H4).
5. **Язык документов.** Три новых документа на русском, остальные спеки на английском. Если исполнители не все русскоязычные — перевести до раздачи.
