_The batch beta — every transfer is one honest row, receivers work in parallel, and projects download from everyone._

## What's New

- **One transfer, one row.** A transfer now keeps a single row for its whole life: resending re-runs the same transfer as "attempt 2, 3, …" instead of stacking duplicates, and history, filters and deletion all follow that one row on both sides. A transfer the receiver declined stays declined — resending it explicitly starts a fresh transfer, so an "are you sure?" on one machine is never silently overridden by another.
- **Receiving from several devices at once.** A second sender no longer waits for the first transfer to finish — transfers from different devices now run in parallel, up to "Simultaneous incoming transfers" (Settings → Sync, default 2, adjustable 1-8 live). Transfers from the same device still arrive strictly in order, and cancelling one transfer no longer waits behind another device's download. Database work is interleaved per file, so one huge incoming batch no longer freezes progress reporting for everything else.
- **Upload speed limit.** Settings → Sync gains "Upload speed limit (MB/s)": one number that caps this device's total sync upload bandwidth so a big transfer never chokes your connection (0 or empty = unlimited, the default). On a Perseus observatory agent set `max_upload_mbps` from the web Settings tab, where it applies instantly, or by hand in perseus.toml — a running agent picks that up within seconds, no restart. A cap of e.g. 8 MB/s keeps SSH responsive while a night's worth of frames uploads. Applies to uploads only; each device's downloads are bounded by the sending device's limit.
- **Transfers say "queued" when that's what they are.** A second batch sent to a busy device now reads "queued at receiver — starts automatically" instead of a retry countdown; the receiving side shows arriving batches the moment they queue (even before downloading starts) and labels transfers waiting for a free download slot as "queued". One word, one meaning: queued = nothing is wrong, it starts by itself.
- **A transfer knows when its peer is away.** The sender now tracks each destination's presence: a transfer to an offline or sleeping machine reads "waiting for the device" instead of burning retry countdowns at a closed door, and the moment that device comes back everything pending to it starts immediately. Retries are saved for peers that are reachable but refusing.
- **Delete and clean up.** Finished, cancelled and failed transfers can be deleted from history on both sides. Settings → Sync shows how much disk transfer data still occupies, and "Clean up finished transfers" reclaims it — leftovers from interrupted downloads included.
- **Perseus web page, rebuilt.** The observatory agent's web UI is now a two-tab page in the app's visual style: Transfers groups every batch across all its target devices with live progress, per-batch details and history delete; Settings collects the agent's knobs. Once a batch is confirmed delivered everywhere — and declined nowhere — a "Delete source files" action removes the originals from the capture machine, and refuses while any delivery is still open. In the app, transfers received from a Perseus agent carry a badge saying so.
- **Project downloads come from everyone.** An approved contribution now downloads from every project member who already has it, in parallel — and if a member goes offline mid-download, the transfer carries on from the others without starting over. Every member who finishes a download automatically helps distribute that package to the rest, so a project gets faster to sync as it grows instead of slower. New approved contributions download by themselves: each project has an "Auto-download contributions" switch (on by default) with the project's published size next to it, a "Sync now" button for an immediate pass, and downloads show how many sources they are pulling from.

## Changes

- **Transfer records written by this version cannot be read by older versions — update every device together.** The first launch after updating resets transfer history and in-flight transfers; your catalog, files and projects are untouched.
- The send dialog gains a batch-name field, and every transfer keeps a per-batch event log — connection noise lives in Details, never in the status line.
- The sidebar sync indicator now reflects transport health, so a device that lost its relay and runs direct-only says so.
- The Discord invite link in About is current.

## Bug Fixes

- **Windows catalogs no longer desync on folder operations.** Sending a folder and renaming a directory built catalog paths with the wrong separator on Windows, leaving the catalog pointing at paths that no longer existed. Both now use the native separator end-to-end, and the scanner repairs alternate spellings of the same file's path instead of cataloguing phantom duplicates.
- **Sign-in works on Windows.** The device-key file lock used a mandatory lock that Windows enforces against the app itself, failing sign-in with "os error 33". The lock moved to a sidecar file.
- **Windows-safe file names.** Generated calibration file names now guard against Windows-reserved names (`CON`, `NUL`, …) and trailing dots; a name collision also checks the catalog, and a failed master registration keeps the built file on disk and tells you where it is.
- **A transfer whose sending device goes offline now shows as waiting for that device, not failed.** The receiving side kept only one word for every interrupted download, so closing the sender mid-transfer painted the row red for a batch the sender was still going to deliver. It now stays in the active list with an honest "waiting for peer" state, keeps what it already received, and resumes on its own when the device comes back — no clicking required. Failed is reserved for what the receiver genuinely cannot accept.
- **The received-files counter climbs during a transfer** instead of reading `0 of 38` until the very end while the per-file bars visibly moved. Files that arrived in a single burst — resumed, already-present, small or empty — were never counted at all.
- A resumed transfer continues from where the sender left off instead of restarting its progress from zero.
- Duplicate detection before a transfer now consults the receiver's whole scanned library, so files the peer already has are skipped reliably — including on the very first transfer to a freshly scanned machine.
